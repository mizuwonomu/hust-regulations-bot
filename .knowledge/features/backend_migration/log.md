# backend_migration — Log

## 2026-08-14 — Decouple the core from Streamlit and give FastAPI ownership of the models

Branch `api-migration`, three commits: 17b247c → 9b0ab52 → 33edb1c.

**Where this started.** The backend already owned conversation title generation, and the goal was to move the rest of the chat path (chain invocation, streaming, memory, sidebar SQL) onto FastAPI so that Streamlit becomes UI only. Surveying the code first showed the actual blocker was not on the FastAPI side at all: `src/rag/qa_chain.py`, `src/rag/embedding_utils.py`, `src/rag/reranker_utils.py` and `src/database/connection.py` all imported Streamlit and used `@st.cache_resource`. Nothing could be handed to another process while the build function and the ownership policy were the same decorator.

**What was done, in order.**

*17b247c — literals to config.* The Groq model ids, the per-stage temperatures, the Chroma path and collection name, and the doc-store path moved out of inline literals in `qa_chain.py` into `src/rag/config.py`; `qa_chain` now imports them. Purely mechanical, chosen as the first commit because it is verifiable on its own (Streamlit answers identically) and because it isolates the one file a future model decommissioning has to touch.

*9b0ab52 — de-Streamlit the rag modules.* `@st.cache_resource` and the Streamlit imports came out of the three `src/rag` modules, leaving plain build functions. `get_chain`'s `_reranker_model` parameter was renamed `reranker_model`, since the leading underscore was only ever a Streamlit hashing convention and becomes misleading once the decorator is gone. To keep Streamlit working unchanged, `frontend/services/model_loader.py` was added: a thin `@st.cache_resource` singleton wrapping the now-pure builders, with `frontend/app.py` pointed at it. This had to be one commit — splitting it would leave an intermediate state where Streamlit rebuilds the chain (BM25 construction plus a full `vector_store.get()`) on every rerun.

*33edb1c — models into the FastAPI lifespan.* `lifespan` now builds the embedding model, the reranker and the RAG chain at startup and parks them on `app.state`, and a `get_rag_chain` dependency reads them back, mirroring the existing `get_db_pool` injector. The commit body records two known limitations rather than hiding them: no route consumes the chain yet, and both processes currently hold their own model copies.

**Verification actually run.** All eight changed files parse. `import src.api.main` succeeds against the project venv and reports all seven routes. `inspect.signature(get_chain)` confirms the renamed parameter. The same import also confirmed that `streamlit` is still pulled into the uvicorn process via `src/database/connection.py` — which is why 9b0ab52's message says `src/` is *not yet* fully Streamlit-free.

## Result

`src/rag` is now runtime-agnostic: the same build functions serve Streamlit (through a transitional shim), the FastAPI lifespan, and the existing `evals/` and `ingestion/` scripts. FastAPI owns a built chain on `app.state` and can inject it. Streamlit behaviour is unchanged for the user.

Against the original definition of done — Streamlit sending a request instead of invoking the chain — this is **step zero plus the model-ownership half of step one**. No chat endpoint exists, the memory layer still runs on a Streamlit-cached sync connection, and the frontend still builds and invokes its own chain. What this feature delivered is the precondition that made the rest possible, plus the proof (a uvicorn process that starts and loads) that the decoupling worked.

## 2026-08-15 — Finish de-Streamliting src/ and add the sync memory pool

Branch `api-migration`, three commits: a46a031 → f765c81 → 41a0a58.

**a46a031 — remove Streamlit from `connection.py`.** `src/database/connection.py` is now a plain sync opener (fresh connection per call, no cache, no streamlit import). The process-wide cache + liveness check moved to `frontend/services/connection_provider.py`, a Streamlit-side shim mirroring `model_loader.py`; `app.py` sources its connection factory from there. This closes step 0: importing `src.api.main` no longer pulls `streamlit` into the uvicorn process. Transitional wart, documented in the file's own docstring: the memory path (`get_session_history`) now opens a fresh connection per turn until it moves onto the pool.

**f765c81 — add the sync pool.** New `src/database/sync_connection.py` builds a sync `ConnectionPool` (min 2 / max 10) with `prepare_threshold=None` (Supavisor 6543 guard) and a checkout liveness check. `lifespan` now opens both pools and parks them on `app.state` as `db_pool` (async) and `sync_db_pool` (sync), closing both on shutdown. The async pool got explicit `min_size=2, max_size=5` to replace the hidden default of 4. No consumer yet — the pool exists for the future `POST /chat` handler.

**41a0a58 — delete dead `background_tasks.py`.** Nothing referenced `fire_and_forget`; title generation runs on FastAPI `BackgroundTasks`. Not migrated because `add_script_run_ctx` solves a Streamlit-only session-context problem.

## Result (as of 2026-08-15)

The connection layer now has three deliberate mechanisms: a Streamlit-side cached single connection (`connection.py` + shim), a FastAPI sync pool (`sync_connection.py`, unconsumed), and the FastAPI async pool (title + SQL). `src/` is fully Streamlit-free. The sync pool is built and lifecycle-managed but not yet wired into memory — that is G2/G3. Definition-of-done progress: step 0 complete, the pool infrastructure for the memory path is in place, and the next move is repointing `get_session_history` at the pool and writing the chat endpoint.

## 2026-08-16 — G2: core chain + per-run history binding

Branch `api-migration`, commit 912e5f1. `get_chain` no longer wraps `RunnableWithMessageHistory`; it returns the core chain (route → retrieve → rerank → answer). A new `bind_history(core_chain, conn)` builds the wrapper per run, binding a caller-supplied connection through `partial(get_session_history, conn)`; `get_session_history` was changed to take `(conn, session_id)` and no longer fetches its own connection. This removes the fresh-connection-per-turn wart G0 left in the memory path.

The Streamlit frontend now does the wrap itself: `chat_flow.handle_query` borrows the cached connection from `deps.db_connection_factory()`, calls `bind_history` on the core chain, and passes the wrapped chain into `render_streamed_ai_answer` — `chat_stream.py` is untouched because it still receives an already-wrapped chain and calls `.stream()`. The dead `debug_memory` util was deleted (it called `get_postgres_history` without a connection).

`app.state.rag_chain` now holds the core chain. The G3 handler will apply the same `bind_history` with a pooled connection per request — one helper, two consumers, differing only in connection source and lifecycle. Verified end-to-end in Streamlit: a context-dependent follow-up ("thế còn miễn giảm?") resolves against the prior turn, so read-at-start and write-at-end both work through the new bind path.

## 2026-08-18 — G3: the chat endpoint

Branch `api-migration`, commits c8654f0 → b4f5988 → 600c3f0. The handler predicted at G2 landed: `POST /conversations/{id}/messages` applies the same `bind_history(core_chain, conn)` the frontend uses, but with a connection borrowed from the lifespan sync pool per request — so the pool finally gets its first consumer. The handler is a plain `def`, letting Starlette run the blocking chain in the threadpool rather than on the event loop, and it borrows a connection twice: once briefly to check ownership and eager-create the conversation row, then again to hold across the chain for memory read/write. Two new sync queries back it — `fetch_conversation_owner` (returns owner or None so absent ≠ owned-by-other) and `claim_conversation` (eager-create with title NULL, ON CONFLICT DO NOTHING, so it never clobbers a title the async path later fills). Owner mismatch returns 404 to avoid leaking existence. The response shape is a deliberate projection: `serialize_sources` maps the chain's parent `Document` objects down to `SourceItem` (title/content/doc_id), keeping the wire contract independent of the Document internals.

Verified by hand through Swagger, not curl, using a real uuid4 conversation id: a regulation question returned an answer with non-empty sources; a chitchat question returned empty sources; a same-id follow-up resolved against history (memory across the pooled per-request connection works); a second `X-User-Id` on an existing conversation returned 404; and the title route reported `status: pending, title: null`, confirming the eager-created row exists without a placeholder title. LangSmith traces were correct.

## Result / outcome — G3

The endpoint exists, is committed, and passes the happy path plus the ownership guard. It is **not** proven under concurrency — session isolation, pool starvation, and disconnect behaviour are unmeasured, and that test is the immediate next step (stubbed LLM, shrunk pool, verify via the `chat_history` table). The feature's own definition-of-done — the Streamlit frontend issuing an HTTP request instead of building and invoking its own chain — remains open; G3 is the endpoint that cutover will target.

## 2026-08-21 — G4: concurrency proof, and the silent-200 bug it exposed

Branch `api-migration`, commits e5748c7 → d31836e → 2241d2b → 8812061.

The concurrency suite that G3 had deferred was already written but had never been run — no test database existed. The prescribed bootstrap (`docker run` a throwaway Postgres on 5433) turned out to be unusable because Docker Desktop's WSL integration was disabled, but a local Postgres was already serving 5432, so the suite was pointed at a `db_testing` database there instead. That satisfied the only real requirement — a reachable Postgres whose name contains `test`, which the `clean_db` fixture demands before it will `TRUNCATE` — and had the side benefit of making the tables inspectable in DBeaver. The first run failed immediately on pool construction: `max_size=2` was set without `min_size`, and psycopg_pool defaults `min_size` to 4, so the intentionally-shrunk pool was rejected as invalid. Pinning `min_size` to the same value fixed it, and the four original probes went green.

What the logs showed was the substance. Requests released in clean 2-2-1 waves about `SLEEP` apart, which is the visual signature of five requests queueing through two connections — and, more importantly, evidence that a request never holds two connections at once. Test (c) printed both facts it exists to record: the turn was still written after the client cancelled, and the pool returned to full capacity.

The DB-side failure probe was then built to close the other half of that story: if a client disconnect leaves a phantom turn, what does a *database* disconnect leave? A `pg_terminate_backend` fired from a separate admin connection, aimed by `application_name` at the pool's own backends and timed to land inside the stub's sleep, answered it — rollback was complete and the pool discarded and replaced the dead connection. But the third assertion failed: the endpoint returned **200 with a normal answer** even though nothing had been written. Reading the langchain_core source explained why. `RunnableWithMessageHistory` attaches the history read as a `RunnableLambda` inside the pipeline and the history write as an `on_end` listener; `CallbackManager.handle_event` logs listener exceptions and only re-raises them when `raise_error` is set, which defaults to `False` and is overridden by no tracer. The write was raising correctly and being discarded one layer up. A misleading detail cost time here: the first of three warnings mentions a psycopg `Pipeline [BAD]`, which looks causal but is only cleanup noise.

The fix threads a caller-owned `MemoryStatus` mailbox down through `bind_history` → `get_session_history` → `get_postgres_history`, where a `TrackedPostgresHistory` subclass records the outcome of `add_messages` before re-raising. The handler creates one mailbox per request, reads it after `invoke`, logs an error with the reason when the write failed, and reports the result as `memory_persisted` on `ChatResponse`. The parameter is optional and defaults to `None`, so the Streamlit path — which shares `bind_history` and therefore shared the bug — inherits the mechanism without a line changed, and simply passes no mailbox.

Implementation was fanned out to three agents in parallel worktrees, all working from the same written design, and the results were compared rather than merged blindly. Reviewing them surfaced a defect none of the agents had caught: the read-failure test kills every pooled connection *before* the request, so the request dies at borrow-1 in `fetch_conversation_owner` and never reaches the history read it claims to cover. The test finishing in ~0.14s against a 0.3s stub sleep is the proof. Rather than write a flaky test to hit the few-millisecond window between the two borrows, the test was renamed and its docstring rewritten to state exactly what it covers and to record that the `_enter_history` guard is still absent.

## Result / outcome — G4

Seven probes pass against the local test database: session isolation, pool starvation, client disconnect, same-session race, DB-side write failure, ownership-read failure, and the happy path. The two-borrow pattern is now measured rather than assumed, and the pool's discard-and-replace behaviour under a killed backend is confirmed. G3's chat endpoint no longer reports success when it has failed to persist a turn; it returns the answer with `memory_persisted=false` and logs the reason server-side.

The three commits were sequenced to preserve the discovery: `d31836e` lands the DB-failure probe as a knowingly-failing test that documents the bug, `2241d2b` turns it green, and `8812061` adds the remaining guards. The concurrency-test half of the definition-of-done is met. The feature's own DoD — the Streamlit frontend calling the endpoint over HTTP instead of invoking its own chain — remains open, and is the next step.


## 2026-08-24 — G5: read-endpoints cutover (step 1 of 3)

Branch `api-migration`, seven commits up to b41c19f. The read path — the sidebar conversation list and loading an old conversation into Streamlit state — stopped querying Postgres directly and now goes over async HTTP: `GET /conversations` and `GET /conversations/{id}/messages`, backed by three async queries (`list_user_conversations`, `fetch_conversation_messages`, `fetch_conversation_owner_and_title_pool`, committed earlier), new Pydantic schemas, and a `frontend/services/conversation_client.py` httpx wrapper. `frontend/` no longer imports `src.database` on the read path — only `connection_provider.py` remains.

The substance that git does not show is the failure-signal plumbing. Load went from hard-fail (the old loader raised and aborted the script) to soft-fail (returns `None`), which forced two changes downstream: the loader now returns `bool`, and the sidebar reruns only on a successful load — without that guard an unconditional `st.rerun()` after a failed load spins forever, because `st.rerun()` discards the current run before `st.error` can paint and the keyless selectbox keeps re-offering the same failed conversation. Ownership is gated in two places on purpose (SQL JOIN for IDOR defence-in-depth, handler owner-lookup to tell owned-empty (200 `[]`) apart from not-yours (404)). The two divergent `_normalize_message` copies were merged into `message_normalizer.py`, which removed the sync-side bug that dropped `jsonb::text` rows. `POOL_TIMEOUT_SECONDS` and the pool-size literals moved into `pool_config.py`, closing the open placement decision and letting the async pool pick up the `prepare_threshold=None` guard it had been missing.

Probe (h) — the event-loop responsiveness arm — is the evidence tied to this slice: it proves the `def` chat handler does not stall the loop, so async read endpoints stay responsive while chat runs. `LoopProbe` must sample on the *same* event loop the app runs on (a probe on another thread would measure a different loop and pass even under a full stall); it has three arms — idle baseline (h1), read latency under N concurrent chat turns (h2), and a negative control (h3) that deliberately blocks the loop to prove the probe can see a stall. Capacity was measured separately at production pool config; because production's 30s pool timeout is unreachable behind the 40-token anyio threadpool gate, the "exceeds" arm has to use a synthetic short timeout to make the pool the binding constraint.

## Result / outcome — G5

Full suite green on the Supabase test schema `regu_test_dsk`: 42 passed / 1 skipped / 2 slow passed (~82s, floored by ~90ms RTT to Supabase — the sub-minute DoD from the plan is void against a real network). Probe (h) read latency under chat load stayed at ratio ~1.02x baseline, well under the 1.0s p95 ceiling — the `def` handler is confirmed not to block the loop. The read path is committed and cut over; `frontend/` touches Postgres only through `connection_provider.py`. The feature's own definition-of-done — the Streamlit **chat** path issuing an HTTP request instead of building and invoking its own chain — remains open and is step 2.

RTT baseline for the test target (2026-08-21, Supabase 6543): `SELECT 1` round-trip p50 ~90ms, p95 ~93ms, max ~100ms (3 rounds x 30, `prepare_threshold=None`); connect + first round-trip ~600-700ms (TLS + auth). Every concurrency-test p95 ceiling stands on this floor — latency from another day is not directly comparable.

## 2026-08-26 — G6: chat cutover (step 2 of 3)

Branch `api-migration`, three commits (`4dcd6f9` client + `http_config`, `67e035e` rewire + deletions, `5bfa875` tests). This is the feature's own definition-of-done: the Streamlit chat turn now issues an HTTP request instead of building and invoking its own chain. Because the G3 endpoint already existed and was proven under concurrency (G4), the slice was frontend-only.

Method worth recording: the implementation was written twice, in two parallel git worktrees (`chat-cutover-1`, `chat-cutover-2`), from a single **logic-only** plan (`docs/superpowers/plans/2026-08-24-chat-cutover-frontend-http.md`) that deliberately withheld code so the two agents' outputs could be compared on merit. Both passed and both fully de-chained the frontend; cutover-2 won the merge on three points — a narrow `except httpx.HTTPError` matching the read client's convention, a semantic (not byte-exact) request-body assertion, and a defensive `render_sources` — while cutover-1's `except Exception`, exact-byte assertion and hard `doc["content"]` access were its weak spots. The merged result took cutover-2 as the base, kept the user's original `doc.get("title", ...)` render shape, and added `http_config` so the timeout/base-URL/header literals are not re-inlined.

The one design decision that carried real weight was the error policy. The client is fail-loud: only 404 and transport/status errors (`httpx.HTTPError`) become `None`; a malformed 200 (missing `answer`, non-JSON) is left to raise, because a body that breaks the backend's own contract should surface in dev rather than be swallowed. Above that, `memory_persisted=false` is treated as a soft degrade — the answer still renders and the UI shows `st.warning`, while a `None` result is the only hard error (`st.error`, no AI message, no title trigger). Streaming was consciously dropped: the endpoint returns one JSON body, so `chat_stream.py` (the old `chain.stream` path) is retired and kept only as the reference surface for the SSE rewrite that is step 3.

## Result / outcome — G6

Six client unit tests pass (`tests/api/test_chat_client.py`, httpx `MockTransport`, no live server or DB): happy-path request shape + 200 parse, 404 and transport error → `None`, `memory_persisted=false` still returns a `ChatResult`, missing `sources` → `[]`, and a malformed 200 missing `answer` raises. `frontend/` no longer imports `src.rag` or `src.database` on any path, and `app.py` loads no models. The feature's definition-of-done (frontend chat over HTTP) is met. Not done, deliberately: the manual Streamlit smoke test was not run in this session, and its degraded-turn `chat_history -> []` arm needs fault injection it cannot reliably do by hand. The remaining work is step 3 — restoring token streaming over SSE.
