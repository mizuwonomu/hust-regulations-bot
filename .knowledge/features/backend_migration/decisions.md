# backend_migration — Decisions

## Chosen approach + why

**Separate "how to build" from "who keeps it", then give each process its own owner** (commits 17b247c → 9b0ab52 → 33edb1c, branch api-migration, 2026-08-14). The blocker to moving anything onto FastAPI was not FastAPI: it was that `@st.cache_resource` in `src/` both *built* the object and *owned* it, so the build could not be reused anywhere else. Splitting those two roles is what unblocked the whole migration.

- Three layers with three different clocks, and they must not be mixed: **`src/rag/config.py` = values** (read once), **`lifespan` = lifecycle and ownership** (startup/shutdown), **`src/api/dependencies.py` = per-request delivery** (must stay dumb: read `app.state`, return it). Model ids specifically belong in `config.py` and *not* in `dependencies.py`, because dependencies re-run every request while a model id is read once — putting them there mixes two clocks.
- Model ids were centralized (17b247c) for a reason recorded elsewhere in `.knowledge`: Groq retires models without notice, so a swap must be a one-file edit. This commit exists to make the *next* decommissioning cheap, not because the current ids are wrong.
- **Sequencing rule adopted:** models enter `lifespan` only when a consumer exists, and the swap must be atomic *per resource* — never a state where both processes own a model, never a state where neither does. Atomic here means **runtime ownership**, not "one giant commit"; the work still split into three commits because each one leaves a running system.
- **That rule was then deliberately broken once.** 33edb1c ships models into `lifespan` with no route consuming them. Accepted because a successfully starting uvicorn is the *only available proof* that `get_chain` builds outside Streamlit — i.e. that 17b247c and 9b0ab52 actually achieved their goal. Without 33edb1c that claim is unverified anywhere.
- **Commit boundary = verifiability boundary, not smallest diff.** Each of the three commits has a check that can be run against it (Streamlit answers identically / Streamlit reruns without reloading models / uvicorn starts and loads). Finer splitting was rejected: removing the cache decorator in one commit and adding the Streamlit shim in the next would leave an intermediate commit where Streamlit rebuilds the chain on every rerun — a landmine for `git bisect` and `git revert`.
- **The Streamlit shim (`frontend/services/model_loader.py`) is deliberate transitional code**, not a permanent layer. `frontend/` is now the only place allowed to know Streamlit exists; `src/` must not. The shim dies in the same change that points the frontend at `POST /chat`.

## Assumptions it rests on

- **Single user, personal project.** Pool starvation, GPU contention on the single CUDA reranker, and the asyncio default-executor ceiling are all real mechanisms but not reachable at this scale. Every "good enough" choice below inherits this assumption; the signal to revisit is more than a handful of concurrent chats.
- **One uvicorn worker.** `app.state` is global *to one process*, exactly like `st.cache_resource`. `--workers N` duplicates bge-m3 and bge-reranker-v2-m3 N times in VRAM. Nothing in the code prevents this.
- **Streamlit and uvicorn are not run at the same time during the transition.** Both processes currently build their own chain, so running both holds two copies of both models.
- **The chain stays LCEL + `RunnableWithMessageHistory`.** Current LangChain docs have moved memory to LangGraph checkpointers (`AsyncPostgresSaver`) and no longer feature `RunnableWithMessageHistory`. Staying on it is a conscious choice: migrating means rewriting the chain, which is a larger job than the backend move. This assumption is the one most likely to expire.
- **Groq round-trips dominate turn latency**, which is what makes async worth adopting later — the win is on the network legs, not on retrieval.

## Failed approaches

- Tried: **keeping `@st.cache_resource` in `src/` and calling those functions from uvicorn** — Failed because: it does not crash. Streamlit falls back to "bare mode" outside its runtime, so memoization still works and only a `missing ScriptRunContext` warning appears; the architecture is wrong invisibly. It also gives lazy loading (first *request* pays the model load, with no spinner and a client timeout), no teardown hook, and silent per-process duplication — Avoid when: tempted because "it works". It demonstrably does: `evals/v2/scripts/*` and `src/ingestion/ingest_regulations.py` have been calling these cached functions via `python -m` with no Streamlit runtime at all, and nobody noticed. **CROSS-CUTTING** — this is a rule about the `src/` boundary, not about this feature.
- Tried: **`functools.lru_cache` on `get_chain`** — Failed because: `embedding_model` is a pydantic v2 object, which defines `__eq__` and is therefore unhashable, and `lru_cache` requires hashable args. This is precisely why the parameter was named `_reranker_model`: the leading underscore was Streamlit's convention for excluding a param from its hash key, not a Python privacy convention — Avoid when: tempted to "cache `get_chain` the same way as the loaders". The leaf loaders take no arguments and *can* use `lru_cache`; `get_chain` cannot, and must be owned by the caller instead.
- Tried: **treating "migrate the SQL" and "build the chat endpoint" as two independent options to prioritize between** — Failed because: there are two different SQL migrations hiding under one name. The *memory* connection (`chat_history` via `PostgresChatMessageHistory`) is a component *inside* `POST /chat` — you cannot write the endpoint without deciding where history gets a connection. Only the *sidebar* SQL is genuinely independent — Avoid when: planning the order of work and the two feel like alternatives.
- Tried: **passing the borrowed DB connection to `get_session_history` through `config["configurable"]`** (via `history_factory_config`, the documented extension point) — Failed because: it puts a live connection object into config, which LangSmith then attempts to serialize into traces, and it muddies the hard rule that `configurable` must never carry client-influenced values. The chosen alternative is to build `full_chain` once in `lifespan` but wrap it in `RunnableWithMessageHistory` **per request**, where the borrowed connection is already in closure scope — viable because the wrapper is cheap while the chain (BM25 build, `vector_store.get()`) is what is expensive — Avoid when: searching for the "official" way to parameterize the history factory.
- Tried: **subclassing `BaseChatMessageHistory` to borrow a pooled connection per operation** — Not failed, deliberately deferred: it is the correct answer at scale (it never holds a connection across the multi-second LLM call) but unnecessary at one user. Chosen instead: borrow in the handler for the whole run, with a generous pool `max_size` — Avoid when: reaching for it before the symptom appears. The symptom to watch for is **the sidebar becoming slow while a chat is in flight** — that is chat holding pooled connections during Groq latency and starving the fast queries. Upgrading later touches only `get_session_history`, so the deferral is cheap.

## Nuances agreed with the user

- **The endpoint *is* the sharing mechanism, not an API wrapper over an already-shared model.** `streamlit run` and `uvicorn` are two OS processes with separate address spaces; a Python object in one is unreachable from the other. "There is no endpoint yet" and "Streamlit cannot use the server's model" are the same sentence, not two facts. This reframes `app.state` as *global to one process*, never "global".
- **`lifespan` is not "the FastAPI version of `cache_resource`".** They solve different problems that happen to produce the same outcome. `cache_resource` exists because Streamlit re-executes the whole script on every interaction; FastAPI has no rerun, so a module-level global would already survive for the process lifetime. What `lifespan` actually buys over a global is: controlled *timing* (after app construction, before serving — not at import), the ability to `await`, and a teardown half.
- **`add_script_run_ctx` in `src/services/background_tasks.py` solves session-state affinity, not caching** — two unrelated problems that look alike. Streamlit has two opposite kinds of memory: `cache_resource` (process-wide, shared by all users) and `session_state` (per browser tab). The ctx copy serves the second. FastAPI has no counterpart because it has no implicit per-session state to locate, so that module is dead code to delete, not to migrate.
- **`st.session_state` has no home on the FastAPI side.** That is the structural reason `conv_id` must travel inside the request, and why ownership checks become mandatory: in Streamlit they were free because `conv_id` never left the process.
- **Sharing one sync psycopg connection is not merely serialization.** psycopg3 locks, so the wire protocol is safe and concurrent callers queue — but they also share one *transaction*. One request's `commit` commits another's unfinished work, and one error puts the connection into aborted-transaction state so every later query fails until a rollback. The hazard already exists in Streamlit today: `cache_resource` is process-global while each session runs in its own thread, so two browser tabs already share it.
- **Async moves the ceiling rather than removing it.** `ChatGroq` is natively async so the three Groq round-trips genuinely release the loop, but sync `RunnableLambda`s (`retreive_parents`) fall back to `run_in_executor`, so blocking moves into asyncio's default thread pool. BM25 scoring is pure Python and therefore GIL-bound; the reranker is a single CUDA model. Async also makes streaming natural (`astream` + `async def` generator), whereas a sync chain requires a *sync* generator so Starlette threadpools it — wrapping a sync chain in an `async def` generator blocks the loop on every `next()`.
- **What this project needs is concurrency testing, not load testing.** Every hazard identified (shared transaction, pool exhaustion, session bleed, message loss on client disconnect) surfaces at N=5; N=1000 adds nothing. Deliberately shrinking pool `max_size` turns rare bugs into reproducible ones. And load-testing the real chain measures Groq's rate limiter rather than this server — the LLM must be stubbed for the test to mean anything.
- **`src/` is not yet Streamlit-free, and this was verified rather than assumed.** After 9b0ab52, importing `src.api.main` still leaves `streamlit` in `sys.modules`, because `qa_chain.py` imports `src/database/connection.py`, which is still `@st.cache_resource`-decorated. The commit message for 9b0ab52 records this honestly rather than overclaiming.

## Connection layer — two sync mechanisms + one async pool (commits a46a031, f765c81, 41a0a58, branch api-migration, 2026-08-15)

**Chosen approach + why.** Finished de-Streamliting `src/` and stood up a sync `ConnectionPool` for the memory path, leaving three distinct connection mechanisms that are *not* redundant:

- `src/database/connection.py` — a plain sync opener (one fresh connection per call), Streamlit-free. Feeds the Streamlit cached singleton via `frontend/services/connection_provider.py` (the shim that re-adds `@st.cache_resource` + the liveness check outside `src/`).
- `src/database/sync_connection.py` — a sync **pool** (min 2 / max 10) for the FastAPI memory path.
- `src/database/async_connection.py` — the async **pool** (min 2 / max 5) for title generation + SQL reads.

The split is along **two axes, not one**: *which process consumes it* (Streamlit vs FastAPI — separate address spaces, cannot share a pool object) and *what shape* (a single cached connection vs a pool). Streamlit historically needs only one connection because it processes one thing at a time; FastAPI needs a pool because it is built for many in-flight requests. **Connection shape tracks the process's concurrency model, not whether the driver call is sync or async.** This is the same two-process split already seen with model loading (`model_loader.py` shim vs lifespan).

- **Two sync mechanisms is transitional, not a design smell.** `get_session_history` currently borrows `connection.py`'s raw opener (uncached, fresh per turn) as a stopgap — documented in that file's docstring. `sync_connection.py` exists precisely to replace that role. Timeline: now → `connection.py` serves both Streamlit and (temporarily) memory; after G2/G3 → memory moves to the sync pool and `connection.py` serves only Streamlit; after frontend→HTTP → `connection.py` dies. Do not try to merge the two sync files: they feed two different processes.

**Assumptions it rests on.**
- **Port 6543 (Supavisor transaction pooler), Supabase 60-connection plan, 1 uvicorn worker.** Peak real connections = (sync max 10 + async max 5) × 1 worker = 15, well under 60. The whole budget assumes 1 worker; `--workers N` multiplies it by N *and* loads N copies of bge-m3 + reranker, so the worker count is pinned at 1 by GPU memory, not by connections.
- **Async pool is smaller than sync on purpose.** Async holds are millisecond (title + SQL reads); the sync memory connection is held across the whole multi-second chat turn. Pool size ≈ hold-time × concurrency, so short holds need fewer connections for the same throughput. This is why copying sync's `max_size` onto async would be over-provisioning, not symmetry.

**Failed approaches / traps.**
- Tried: **leaving the async pool's `max_size` at its hidden default** — Failed because: `psycopg_pool` defaults `max_size` to `None`, which collapses to `min_size` (4), so the pool silently cannot grow past 4 and this is invisible in the code — Avoid when: reading pool code and assuming an unset `max_size` means "unbounded". Now set explicitly to 2/5.
- Trap recorded, not yet hit: **psycopg3 auto-promotes queries to server-side prepared statements after `prepare_threshold` (default 5) uses**, which breaks under Supavisor transaction mode because the real connection is swapped between clients per transaction → intermittent `prepared statement "_pg3_x" already exists` under load only. Guarded in `sync_connection.py` with `prepare_threshold=None`. **The async pool does NOT yet carry this guard** — it must be added there too before the async pool is used over 6543 at any real concurrency. **CROSS-CUTTING** (any pool over 6543).

**Nuances agreed with the user.**
- **Supavisor's 200 virtual connections are not 200 parallel workers.** It exploits the fact that a chat turn holds a DB connection only in millisecond bursts (the multi-second Groq wait is idle), returning the real connection to a small pool the instant each transaction ends. 200 = people in the room; ~15 = open counters. It converts "connection refused" into "queued", which is exactly the desired behaviour for concurrency testing — but the 200 is not throughput.
- **The transaction hazard of a shared connection already exists in Streamlit today**, just rarely: `cache_resource` is process-global while each session runs its own thread, so two tabs touching the DB at the same instant already share one connection and one transaction. FastAPI turns rare into constant.
