# backend_migration — Decisions

## Chosen approach + why

**Separate "how to build" from "who keeps it", then give each process its own owner** (commits 17b247c → 9b0ab52 → 33edb1c, branch api-migration, 2026-08-14). The blocker to moving anything onto FastAPI was not FastAPI: it was that `@st.cache_resource` in `src/` both *built* the object and *owned* it, so the build could not be reused anywhere else. Splitting those two roles is what unblocked the whole migration.

- Three layers with three different clocks, and they must not be mixed: **`src/rag/config.py` = values** (read once), **`lifespan` = lifecycle and ownership** (startup/shutdown), **`src/api/dependencies.py` = per-request delivery** (must stay dumb: read `app.state`, return it). Model ids specifically belong in `config.py` and *not* in `dependencies.py`, because dependencies re-run every request while a model id is read once — putting them there mixes two clocks.
- Model ids were centralized (17b247c) for a reason recorded elsewhere in `.knowledge`: Groq retires models without notice, so a swap must be a one-file edit. This commit exists to make the *next* decommissioning cheap, not because the current ids are wrong.
- **Sequencing rule adopted:** models enter `lifespan` only when a consumer exists, and the swap must be atomic *per resource* — never a state where both processes own a model, never a state where neither does. Atomic here means **runtime ownership**, not "one giant commit"; the work still split into three commits because each one leaves a running system.
- **That rule was then deliberately broken once.** 33edb1c ships models into `lifespan` with no route consuming them. Accepted because a successfully starting uvicorn is the *only available proof* that `get_chain` builds outside Streamlit — i.e. that 17b247c and 9b0ab52 actually achieved their goal. Without 33edb1c that claim is unverified anywhere.
- **Commit boundary = verifiability boundary, not smallest diff.** Each of the three commits has a check that can be run against it (Streamlit answers identically / Streamlit reruns without reloading models / uvicorn starts and loads). Finer splitting was rejected: removing the cache decorator in one commit and adding the Streamlit shim in the next would leave an intermediate commit where Streamlit rebuilds the chain on every rerun — a landmine for `git bisect` and `git revert`.
- **The Streamlit shim (`frontend/services/model_loader.py`) is deliberate transitional code**, not a permanent layer. `frontend/` is now the only place allowed to know Streamlit exists; `src/` must not. The shim dies in the same change that points the frontend at `POST /chat`.

## Assumptions it rests on

- **Single user, personal project.** Pool starvation, GPU contention on the single CUDA reranker, and the asyncio default-executor ceiling are all real mechanisms but not reachable at this scale. Every "good enough" choice below inherits this assumption; the signal to revisit is more than a handful of concurrent chats.
- **One uvicorn worker.** `app.state` is global *to one process*, exactly like `st.cache_resource`. `--workers N` duplicates bge-m3 and bge-reranker-v2-m3 N times in VRAM. Nothing in the code prevents this.
- **Streamlit and uvicorn are not run at the same time during the transition.** Both processes currently build their own chain, so running both holds two copies of both models.
- **The chain stays LCEL + `RunnableWithMessageHistory`.** Current LangChain docs have moved memory to LangGraph checkpointers (`AsyncPostgresSaver`) and no longer feature `RunnableWithMessageHistory`. Staying on it is a conscious choice: migrating means rewriting the chain, which is a larger job than the backend move. This assumption is the one most likely to expire.
- **Groq round-trips dominate turn latency**, which is what makes async worth adopting later — the win is on the network legs, not on retrieval.

## Failed approaches

- Tried: **keeping `@st.cache_resource` in `src/` and calling those functions from uvicorn** — Failed because: it does not crash. Streamlit falls back to "bare mode" outside its runtime, so memoization still works and only a `missing ScriptRunContext` warning appears; the architecture is wrong invisibly. It also gives lazy loading (first *request* pays the model load, with no spinner and a client timeout), no teardown hook, and silent per-process duplication — Avoid when: tempted because "it works". It demonstrably does: `evals/v2/scripts/*` and `src/ingestion/ingest_regulations.py` have been calling these cached functions via `python -m` with no Streamlit runtime at all, and nobody noticed. **CROSS-CUTTING** — this is a rule about the `src/` boundary, not about this feature.
- Tried: **`functools.lru_cache` on `get_chain`** — Failed because: `embedding_model` is a pydantic v2 object, which defines `__eq__` and is therefore unhashable, and `lru_cache` requires hashable args. This is precisely why the parameter was named `_reranker_model`: the leading underscore was Streamlit's convention for excluding a param from its hash key, not a Python privacy convention — Avoid when: tempted to "cache `get_chain` the same way as the loaders". The leaf loaders take no arguments and *can* use `lru_cache`; `get_chain` cannot, and must be owned by the caller instead.
- Tried: **treating "migrate the SQL" and "build the chat endpoint" as two independent options to prioritize between** — Failed because: there are two different SQL migrations hiding under one name. The *memory* connection (`chat_history` via `PostgresChatMessageHistory`) is a component *inside* `POST /chat` — you cannot write the endpoint without deciding where history gets a connection. Only the *sidebar* SQL is genuinely independent — Avoid when: planning the order of work and the two feel like alternatives.
- Tried: **passing the borrowed DB connection to `get_session_history` through `config["configurable"]`** (via `history_factory_config`, the documented extension point) — Failed because: it puts a live connection object into config, which LangSmith then attempts to serialize into traces, and it muddies the hard rule that `configurable` must never carry client-influenced values. The chosen alternative is to build `full_chain` once in `lifespan` but wrap it in `RunnableWithMessageHistory` **per request**, where the borrowed connection is already in closure scope — viable because the wrapper is cheap while the chain (BM25 build, `vector_store.get()`) is what is expensive — Avoid when: searching for the "official" way to parameterize the history factory.
- Tried: **subclassing `BaseChatMessageHistory` to borrow a pooled connection per operation** — Not failed, deliberately deferred: it is the correct answer at scale (it never holds a connection across the multi-second LLM call) but unnecessary at one user. Chosen instead: borrow in the handler for the whole run, with a generous pool `max_size` — Avoid when: reaching for it before the symptom appears. The symptom to watch for is **the sidebar becoming slow while a chat is in flight** — that is chat holding pooled connections during Groq latency and starving the fast queries. Upgrading later touches only `get_session_history`, so the deferral is cheap.

## Nuances agreed with the user

- **The endpoint *is* the sharing mechanism, not an API wrapper over an already-shared model.** `streamlit run` and `uvicorn` are two OS processes with separate address spaces; a Python object in one is unreachable from the other. "There is no endpoint yet" and "Streamlit cannot use the server's model" are the same sentence, not two facts. This reframes `app.state` as *global to one process*, never "global".
- **`lifespan` is not "the FastAPI version of `cache_resource`".** They solve different problems that happen to produce the same outcome. `cache_resource` exists because Streamlit re-executes the whole script on every interaction; FastAPI has no rerun, so a module-level global would already survive for the process lifetime. What `lifespan` actually buys over a global is: controlled *timing* (after app construction, before serving — not at import), the ability to `await`, and a teardown half.
- **`add_script_run_ctx` in `src/services/background_tasks.py` solves session-state affinity, not caching** — two unrelated problems that look alike. Streamlit has two opposite kinds of memory: `cache_resource` (process-wide, shared by all users) and `session_state` (per browser tab). The ctx copy serves the second. FastAPI has no counterpart because it has no implicit per-session state to locate, so that module is dead code to delete, not to migrate.
- **`st.session_state` has no home on the FastAPI side.** That is the structural reason `conv_id` must travel inside the request, and why ownership checks become mandatory: in Streamlit they were free because `conv_id` never left the process.
- **Sharing one sync psycopg connection is not merely serialization.** psycopg3 locks, so the wire protocol is safe and concurrent callers queue — but they also share one *transaction*. One request's `commit` commits another's unfinished work, and one error puts the connection into aborted-transaction state so every later query fails until a rollback. The hazard already exists in Streamlit today: `cache_resource` is process-global while each session runs in its own thread, so two browser tabs already share it.
- **Async moves the ceiling rather than removing it.** `ChatGroq` is natively async so the three Groq round-trips genuinely release the loop, but sync `RunnableLambda`s (`retreive_parents`) fall back to `run_in_executor`, so blocking moves into asyncio's default thread pool. BM25 scoring is pure Python and therefore GIL-bound; the reranker is a single CUDA model. Async also makes streaming natural (`astream` + `async def` generator), whereas a sync chain requires a *sync* generator so Starlette threadpools it — wrapping a sync chain in an `async def` generator blocks the loop on every `next()`.
- **What this project needs is concurrency testing, not load testing.** Every hazard identified (shared transaction, pool exhaustion, session bleed, message loss on client disconnect) surfaces at N=5; N=1000 adds nothing. Deliberately shrinking pool `max_size` turns rare bugs into reproducible ones. And load-testing the real chain measures Groq's rate limiter rather than this server — the LLM must be stubbed for the test to mean anything.
- **`src/` is not yet Streamlit-free, and this was verified rather than assumed.** After 9b0ab52, importing `src.api.main` still leaves `streamlit` in `sys.modules`, because `qa_chain.py` imports `src/database/connection.py`, which is still `@st.cache_resource`-decorated. The commit message for 9b0ab52 records this honestly rather than overclaiming.

## Connection layer — two sync mechanisms + one async pool (commits a46a031, f765c81, 41a0a58, branch api-migration, 2026-08-15)

**Chosen approach + why.** Finished de-Streamliting `src/` and stood up a sync `ConnectionPool` for the memory path, leaving three distinct connection mechanisms that are *not* redundant:

- `src/database/connection.py` — a plain sync opener (one fresh connection per call), Streamlit-free. Feeds the Streamlit cached singleton via `frontend/services/connection_provider.py` (the shim that re-adds `@st.cache_resource` + the liveness check outside `src/`).
- `src/database/sync_connection.py` — a sync **pool** (min 2 / max 10) for the FastAPI memory path.
- `src/database/async_connection.py` — the async **pool** (min 2 / max 5) for title generation + SQL reads.

The split is along **two axes, not one**: *which process consumes it* (Streamlit vs FastAPI — separate address spaces, cannot share a pool object) and *what shape* (a single cached connection vs a pool). Streamlit historically needs only one connection because it processes one thing at a time; FastAPI needs a pool because it is built for many in-flight requests. **Connection shape tracks the process's concurrency model, not whether the driver call is sync or async.** This is the same two-process split already seen with model loading (`model_loader.py` shim vs lifespan).

- **Two sync mechanisms is transitional, not a design smell.** `get_session_history` currently borrows `connection.py`'s raw opener (uncached, fresh per turn) as a stopgap — documented in that file's docstring. `sync_connection.py` exists precisely to replace that role. Timeline: now → `connection.py` serves both Streamlit and (temporarily) memory; after G2/G3 → memory moves to the sync pool and `connection.py` serves only Streamlit; after frontend→HTTP → `connection.py` dies. Do not try to merge the two sync files: they feed two different processes.

**Assumptions it rests on.**
- **Port 6543 (Supavisor transaction pooler), Supabase 60-connection plan, 1 uvicorn worker.** Peak real connections = (sync max 10 + async max 5) × 1 worker = 15, well under 60. The whole budget assumes 1 worker; `--workers N` multiplies it by N *and* loads N copies of bge-m3 + reranker, so the worker count is pinned at 1 by GPU memory, not by connections.
- **Async pool is smaller than sync on purpose.** Async holds are millisecond (title + SQL reads); the sync memory connection is held across the whole multi-second chat turn. Pool size ≈ hold-time × concurrency, so short holds need fewer connections for the same throughput. This is why copying sync's `max_size` onto async would be over-provisioning, not symmetry.

**Failed approaches / traps.**
- Tried: **leaving the async pool's `max_size` at its hidden default** — Failed because: `psycopg_pool` defaults `max_size` to `None`, which collapses to `min_size` (4), so the pool silently cannot grow past 4 and this is invisible in the code — Avoid when: reading pool code and assuming an unset `max_size` means "unbounded". Now set explicitly to 2/5.
- Trap recorded, not yet hit: **psycopg3 auto-promotes queries to server-side prepared statements after `prepare_threshold` (default 5) uses**, which breaks under Supavisor transaction mode because the real connection is swapped between clients per transaction → intermittent `prepared statement "_pg3_x" already exists` under load only. Guarded in `sync_connection.py` with `prepare_threshold=None`. **The async pool does NOT yet carry this guard** — it must be added there too before the async pool is used over 6543 at any real concurrency. **CROSS-CUTTING** (any pool over 6543).

**Nuances agreed with the user.**
- **Supavisor's 200 virtual connections are not 200 parallel workers.** It exploits the fact that a chat turn holds a DB connection only in millisecond bursts (the multi-second Groq wait is idle), returning the real connection to a small pool the instant each transaction ends. 200 = people in the room; ~15 = open counters. It converts "connection refused" into "queued", which is exactly the desired behaviour for concurrency testing — but the 200 is not throughput.
- **The transaction hazard of a shared connection already exists in Streamlit today**, just rarely: `cache_resource` is process-global while each session runs its own thread, so two tabs touching the DB at the same instant already share one connection and one transaction. FastAPI turns rare into constant.

## G2 — core chain + `bind_history` helper (commit 912e5f1, branch api-migration, 2026-08-16)

The core *why* was already recorded above (the "pass the connection via `configurable`" failed approach and the chosen "build `full_chain` once, wrap `RunnableWithMessageHistory` per request"). G2 implemented it. Two new decisions worth recording:

- **`bind_history` lives in `src/rag/qa_chain.py`, not `frontend/` or `src/api/`.** The helper must be importable by *both* consumers (Streamlit frontend and the future FastAPI handler), and the layering rule forbids the obvious-looking homes: `src/` must not import `frontend/`, and a frontend importing `src/api/` is backwards. The only shared vantage point is `src/`. Within `src/`, it sits next to `get_session_history` and the core chain because the three message keys (`question`/`chat_history`/`answer`) are defined by how `get_chain` builds the chain — splitting the helper into another module would put those keys in two files that must be kept in sync.
- **Streamlit stays in-process at G2 rather than cutting to HTTP.** Returning the core chain forced a frontend change (it must now wrap history itself). The tempting reaction — "just move the frontend to `POST /chat` now" — was rejected because it couples endpoint + streaming + memory + frontend rewrite into one unverifiable step. A single shared `bind_history` defuses the duplication that would otherwise justify going HTTP: the frontend and the handler call the *same* helper, so keeping the frontend in-process costs no duplicated wrap logic. Frontend→HTTP is deferred to its own clean step after the endpoint is proven. Keeping the in-process path alive is a safety net, not debt: it is the working baseline to diff the endpoint against.

**Nuance.** The frontend wrap is localized to `chat_flow.handle_query` (borrow cached conn → `bind_history` → pass wrapped chain down); `chat_stream.py` is untouched because it still receives an already-wrapped chain. All entry points (hero buttons, `prompt_trigger`, chat input) funnel through `handle_query`, so one wrap site covers them. The dead `debug_memory` util was removed in passing — it called `get_postgres_history` without a connection and had no caller.

## G3 — the chat endpoint (2026-08-18)

`POST /conversations/{id}/messages` shipped as commits c8654f0 (db queries) → b4f5988 (schemas) → 600c3f0 (endpoint + wiring), branch api-migration. Split into three bisectable commits: each imports cleanly on its own, the route (which imports both queries and schemas) landing last.

**Chosen decisions + why.**
- **Handler is a plain `def`, not `async def`.** The core chain is sync and blocking (`ChatGroq.invoke` network I/O, `reranker.predict` CPU, Chroma). A `def` handler is dispatched by Starlette to the anyio threadpool, keeping the event loop free; an `async def` would run that blocking work *on* the single event-loop thread and freeze the whole server for every concurrent request. For a blocking chain, `def` is the more scalable choice, not the lazy one. Going async is only worth it once the GPU/embedding work leaves the process (see the serving-layer note) — otherwise `ainvoke` still parks CPU-bound rerank on a thread anyway.
- **Two-borrow connection pattern.** Borrow 1 (short): ownership check + eager-create, connection released immediately. Borrow 2 (long): `bind_history(core_chain, conn)` + `invoke`, holding the connection across the whole chain because memory reads history at the start and writes at the end. Splitting them keeps a pooled connection from being pinned for the entire LLM call just to do a cheap ownership check up front — under load that single-borrow version would exhaust the pool fast.
- **Ownership mismatch returns 404, not 403.** 403 ("exists but forbidden") leaks the conversation's existence; 404 hides it. This is the IDOR guard, and it is only as strong as the identity feeding it — `X-User-Id` is currently an unauthenticated, spoofable header, so the guard is a placeholder until real auth lands.
- **`claim_conversation` (DO NOTHING) is separate from `insert_title_conversations` (DO UPDATE).** Eager-create at the first message establishes the row + owner *before any title exists*, closing the window where no row means no enforceable ownership. It must be DO NOTHING so it never clobbers an already-generated title; the title path's DO UPDATE only touches `title`, so the two compose — claim owns `user_id`, the title upsert owns `title`, neither overwrites the other's field.
- **`serialize_sources` projects, it does not pass through.** The chain returns `result["context"]` as LangChain `Document` objects carrying surplus metadata (`rerank_score`, `dieu`, `ap_dung_*`…); the endpoint maps them to a 3-field `SourceItem` (title/content/doc_id) matching the frontend source panel. This is an anti-corruption boundary — the wire contract does not move when the Document shape does.

**Assumptions it rests on.**
- The endpoint is `invoke` (one-shot), not streaming. The Streamlit UI streams; when the frontend cuts to HTTP and wants to keep token-by-token, this handler needs an `astream` + SSE variant, which is a different handler.
- The two-borrow path is correct under concurrency — **unverified**. Session isolation, pool starvation behaviour, and connection leaks on client disconnect are reasoned about, not measured. The concurrency test is the next step.
- Ownership is enforced *by the handler*. `get_session_history` and `get_conversation_messages` still do no owner check themselves; safe only because the handler gates them before invoke.

**Nuance.** This is the first consumer of the sync pool (`app.state.sync_db_pool`), which was built and lifecycle-managed since G0 but unused. The feature's real definition-of-done — frontend sending an HTTP request instead of invoking its own chain — is still open; G3 only builds the endpoint the frontend will call.

## G4 — concurrency proof + the memory-persist signal (2026-08-21)

Two linked pieces of work on branch `api-migration`: the concurrency test that G3 was waiting on (commits e5748c7, then d31836e), and the bug that test exposed plus its fix (commits 2241d2b → 8812061).

**Chosen decisions + why.**

- **Two-borrow is sequential, not nested — and test (b) is the regression guard that keeps it so** (commit e5748c7). A request releases borrow-1 before taking borrow-2, so it never holds more than one connection at a time. That is what makes it immune to pool deadlock: a *nested* double-borrow at `max_size=N` deadlocks with N concurrent requests, each pinning one connection while waiting for a second that can never arrive. Measured, not assumed: 5 concurrent requests against a 2-connection pool all returned 200 and released in 2-2-1 waves ~`SLEEP` apart, with the pool probe confirming `requests_waiting` reached at least 3.
- **Client disconnect is an argument *for* keeping the handler sync `def`** (commit e5748c7). Cancelling the asyncio task does not kill the threadpool thread, so the handler runs to completion: the connection is returned clean and the write COMMITs — a "phantom turn" the client believes it cancelled. The alternative failure mode (being cut mid-transaction, leaving a half-written turn or a leaked connection) is worse than a phantom turn. Test (c) therefore hard-asserts only the no-leak property and merely *records* the phantom write, because the phantom write is inherent to the `def` choice rather than a defect.
- **A failed memory write returns 200 with a flag, not 500** (commit 2241d2b). A chat turn has two separable outcomes: the answer (succeeded, and cost real LLM money) and the memory write (failed). Failing the whole request throws away a valid answer to punish a bookkeeping error. `ChatResponse` gained `memory_persisted` so the backend states what actually happened; presenting that as a hard error, a soft warning, or a silent retry is a downstream UX decision.
- **The signal travels in a caller-owned mailbox (`MemoryStatus`), threaded as an optional keyword** (commit 2241d2b). The handler cannot reach the history object at all — `RunnableWithMessageHistory` calls the `partial(get_session_history, conn)` factory internally — so the flag has to ride on something the caller hands *down*. Alternatives rejected: a `ContextVar` (no signature change, but implicit, and a missed reset leaks state between requests — exactly the class of bug being fixed), and checking `conn.broken` after invoke (fewest lines, but it tests a *proxy* for health rather than the *invariant*; a write that fails for a non-connection reason — constraint, disk, serialization — still slips through as 200).
- **Subclass rather than wrap** (commit 2241d2b). `TrackedPostgresHistory` overrides `__init__` and `add_messages` only; every other method is inherited untouched. Composition would require forwarding each method `RunnableWithMessageHistory` might call, which is more surface to get wrong. `add_messages` still re-raises after recording, so semantics and LangChain's own warning log are preserved — the flag is the part that actually escapes.
- **Kill the backend from an admin connection, in the stub's sleep window, before the write** (commit d31836e). There is no client-side API to "break" a connection, so the fault is injected with `pg_terminate_backend` from a separate `psycopg.connect` that is deliberately *not* from the pool under measurement. Pool connections are tagged `application_name='hust-test-kill'` so the kill targets them precisely. Killing during the sleep — before any write has begun — makes the assertion unambiguous (zero rows, not "half a write"); killing mid-write would be timing-fragile and would really be testing langchain's commit behaviour rather than the G3 path.

**Assumptions it rests on.**

- The concurrency tests measure the *server*, not the model: the LLM is a stub that sleeps `SLEEP`, the pool is deliberately shrunk to `max_size=2`, and `POOL_TIMEOUT` must stay above `3 × SLEEP` or the starvation test starts measuring timeouts instead of queueing.
- Fault injection covers only faults the client can *detect*: `pg_terminate_backend` models a server closing the socket cleanly. A silent network drop (TCP half-open — cut cable, firewall DROP) leaves psycopg unaware until TCP timeout and is **not** covered; that needs packet-level injection (iptables, toxiproxy).
- The flag is only useful if the client reads it. Nothing forces that, so server-side error logging is the backstop.
- `MemoryStatus` must be constructed per request. Reusing one across requests reports the previous turn's outcome.

**Failed approaches.**

- Tried: asserting the DB-side write failure surfaces as **HTTP 500** — Failed because: the exception never reaches the handler at all (LangChain swallows listener exceptions), so the endpoint returns 200 and the assertion can never pass, no matter how the handler is written — Avoid when: writing any test that expects an error raised inside a LangChain callback/listener to become an HTTP status. Assert on an explicit signal instead. **Cross-cutting** — see the pointer in `index.md`.
- Tried: diagnosing the swallow as psycopg's `Pipeline [BAD]` (the warning that appears first in the log) — Failed because: `add_messages` is a plain `executemany` + `commit` and *does* raise `OperationalError`; the `Pipeline [BAD]` line is psycopg cleanup noise, and the actual swallow is `CallbackManager.handle_event` — Avoid when: the top line of a stack of warnings looks like the cause. Here the order of the three warnings (pipeline cleanup → callback error → pool discard) is misleading.
- Tried: testing the history-read failure by killing every pool connection before the request — Failed because: it does prove *a* read failure surfaces, but the failure happens at borrow-1 (`fetch_conversation_owner`), never reaching `load_history` in borrow-2. Proof: the test completes in ~0.14s while the stub sleeps 0.3s, so `invoke` was never entered — Avoid when: someone reads `test_f` and assumes `_enter_history` is guarded. It is not; that guard is still missing (see tracker debt).
- Tried: pointing `TEST_DATABASE_URL` at a Docker-run throwaway Postgres, per the earlier handoff — Failed because: Docker Desktop's WSL integration was off in this distro, and a local Postgres was already listening on 5432 — Avoid when: a handoff prescribes `docker run` for a test DB. The test needs only a reachable Postgres whose dbname contains `test`; using the local instance also makes the data inspectable in DBeaver.

**Nuances agreed with the user.**

- The severity was deliberately downgraded mid-review. "Silent data loss" was wrong: the normal path persists correctly (confirmed against Supabase and LangSmith traces). The defect is **false success under fault** — a resilience/observability gap that only fires when a DB fault lands in the write window — not a standing data-integrity bug. The distinction matters because it sets the priority.
- `context: []` in a LangSmith trace is *not* evidence of a memory failure. It is the RAG source list, and the stub always returns it empty. The two were being conflated while diagnosing.
- The read path deliberately gets **no** flag. Read failures already propagate, and swallowing-then-flagging them would recreate the exact bug being fixed. Rule of thumb recorded for later: *the write needs a flag because it is swallowed; the read does not because it is not.*
- Test `(c)`'s phantom turn and test `(e)`'s DB fault are opposite outcomes and must not be conflated: in `(c)` the write succeeds and the connection survives; in `(e)` the write does not happen and the connection is discarded and replaced.
- Three agents implemented the same design in parallel worktrees. The merged result takes `TrackedPostgresHistory.__init__` from the variant that forwards `**kwargs` (another variant hard-coded `sync_connection=`, silently narrowing the parent, which accepts `async_connection` too) and the honest `test_f` docstring from the variant that named `fetch_conversation_owner` as the real failure point. A third variant was dropped for wrapping its privilege check in `except Exception` — any error became a `skip`, which hides failures.


## G5 — read-endpoints cutover, step 1 of 3 (2026-08-24)

Read path moved off Postgres onto async HTTP. Branch `api-migration`, seven commits up to b41c19f (pool_config → message_normalizer → conversation schemas → conversation routes → conversation_client → frontend sidebar/loader → tests). The Streamlit sidebar list and loading an old conversation now call `GET /conversations` and `GET /conversations/{id}/messages` instead of importing `src.database`. Step 1 of a 3-step cutover (step 2 = chat POST cutover, step 3 = SSE).

**Chosen decisions + why.**

- **Ownership is enforced twice, and both layers are load-bearing for different reasons.** The SQL read (`fetch_conversation_messages`) JOINs `conversations` and filters `c.user_id`, so a non-owner gets `[]` even if a future handler forgets to check — this is the IDOR gate, proven by a test that calls the query directly, bypassing the handler. But the handler *also* looks up the owner separately (`fetch_conversation_owner_and_title_pool`) and returns 404 on mismatch, because the SQL gate alone cannot distinguish "empty because not yours" from "empty because you own it but it has no messages" — both come back `[]`. Owned-but-empty must be 200 `[]`; unknown/not-yours must be 404. Only the handler lookup separates those. Drop either layer and one breaks: no SQL gate → IDOR if a handler forgets the filter; no handler lookup → owned-empty conversations wrongly 404.
- **404 (not 403) for non-owner and unknown alike**, matching the chat endpoint — hide existence, don't leak it. Same spoofable-`X-User-Id` caveat as G3: the guard is only as strong as the identity feeding it.
- **`None` vs `[]` is a three-layer contract.** `conversation_client`: `None` = request failed (transport dead / 404), `[]` = succeeded but empty. `fetch_messages` maps 404 to `None` *separately* from transport errors (logged as a warning, since 404 means "not yours / not there" by design, not an outage). `load_conversation_into_state` collapses both `None` cases into one `st.error` + `return False` — from the UI's view both are simply "can't open this conversation".
- **The loader returns `bool` and the sidebar reruns only on success — this is a loop guard, not cosmetics.** It exists *because* the HTTP cutover changed load from hard-fail to soft-fail: the old direct-DB loader raised on failure (which aborts the Streamlit script), the new one returns `None`. With a soft-fail, an unconditional `st.rerun()` after a failed load loops — `st.rerun()` raises immediately and discards the current run, so the `st.error` never paints; the keyless selectbox retains the user's pick while `conv_id` in state is unchanged, so the next run re-enters the same failed branch and reruns again, forever. Gating the rerun on the `bool` both lets the error render and stops the loop. (The neighbouring comment claiming the keyless selectbox "resets to display_id via index each rerun" is the shakier belief: `index` only sets the *initial* default; the widget persists the user's selection across reruns, which is exactly why the loop is real and the guard is needed.)
- **One normalizer, `src/database/message_normalizer.py`.** The sync (`conversation_queries`) and async (`conversation_queries_async`) paths each carried their own `_normalize_message` and had diverged. Merging removed a real bug in the sync copy: it parsed a JSON-string row successfully into `parsed_message` but then tested `raw_message` (still a `str`) for dict-ness and returned `None`, silently dropping rows that arrive as `jsonb::text`. The unified version checks `parsed_message` throughout, returns `None` (never raises) for any unusable row, and both query layers skip `None` rows.
- **`src/database/pool_config.py` resolves the earlier OPEN DECISION on `POOL_TIMEOUT_SECONDS` placement.** It previously lived in `sync_connection.py` with `async_connection.py` importing it — a wrong-direction sibling dependency; duplicating the literal would recreate the divergence bug just fixed in the normalizer. The agreed third option shipped: min/max sizes and the timeout are constants in `pool_config`, both pools import them. The async pool also finally gained the `prepare_threshold=None` guard here, since the read endpoints make it the async pool's second consumer (its first real concurrency).

**Assumptions it rests on.**
- Only the *read* path is cut over. The chat POST and title flow still run their existing routes; Streamlit still builds and invokes its own chain for chatting. `grep "from src.database" frontend/` is down to `connection_provider.py` alone.

- Latency figures rest on the Supabase test target's RTT floor (~90ms), not localhost intuition.

## G6 — chat cutover (step 2 of 3): frontend chat over HTTP (2026-08-26)

**Chosen approach + why.** The Streamlit chat turn now calls `POST /conversations/{id}/messages` through a thin sync httpx client (`frontend/services/chat_client.py`) instead of building and invoking its own chain in-process (commits `4dcd6f9` client + `http_config`, `67e035e` rewire + deletions, `5bfa875` tests, branch `api-migration`, 2026-08-26). The endpoint already existed from G3, so this slice was frontend-only. Implementation was fanned out to two parallel worktrees (`chat-cutover-1`, `chat-cutover-2`) from the same logic-only plan (`docs/superpowers/plans/2026-08-24-chat-cutover-frontend-http.md`); **cutover-2 was chosen as the merge base** because its narrow `except httpx.HTTPError` matched the sibling read client's convention, its test asserted the request body semantically (not byte-exact), and its `render_sources` was defensive — cutover-1's `except Exception`, exact-byte body assertion, and hard `doc["content"]` access were the reasons it lost.

- **Fail-loud on a malformed 200, chosen over graceful-`None`.** The client returns `None` only for 404 and transport/HTTP-status errors (`httpx.HTTPError`); a 200 whose body is non-JSON or missing the required `answer` is left to raise (`ValueError`/`KeyError`). Reason: the backend is ours, so a body that violates its own contract is a bug we want to see surface in dev, not one masked as a silent failed turn. A blanket `except Exception` was explicitly rejected — it also swallows real programming bugs and `KeyboardInterrupt`. `answer` is hard-accessed (required); `sources` defaults to `[]`; `memory_persisted` coerces to bool.
- **`memory_persisted=false` is a soft degrade, not a failure.** Answer generation succeeds server-side even when the memory write fails, so the client still returns a `ChatResult` (never `None`) and the UI shows `st.warning` under the answer while keeping it. `None` (404/transport) is the only hard-error path (`st.error`, no AI message appended, no title trigger, so the user can simply re-ask).
- **Shared `http_config.py` instead of re-inlined literals.** Base URL, the `X-User-Id` header helper, and a 4-phase chat timeout live in one module; the new client imports them. The timeout is split by phase deliberately: only `read` is long (120s, the phase that covers the server-side LLM call), while `connect`/`write`/`pool` stay short so a dead backend fails fast rather than hanging the UI for two minutes.
- **Frontend fully decoupled from the chain.** With chat over HTTP, `rag_chain` and `db_connection_factory` left `AppDeps`, and `model_loader.py` + `connection_provider.py` were deleted. This is the feature's real DoD (frontend no longer builds its own chain) and it ends the double model-load when Streamlit and uvicorn run together.

**Assumptions it rests on.**
- The wire contract `ChatResponse = {answer, sources:[{title,content,doc_id}], memory_persisted}` is stable; `answer` is always present on a 200 (fail-loud depends on this being a real contract, not a soft field).
- Losing token-streaming is acceptable for now. The `POST` returns one JSON body, so the UI renders the whole answer at once until SSE (step 3) restores streaming.
- `X-User-Id` identity is still the fixed spoofable dev header; the cutover adds no auth.

**Failed / rejected approaches.**
- Tried: reordering `ChatResponse` fields (sources first, `memory_persisted` last) to prepare for streaming. Failed because: a Pydantic `response_model` is serialized and sent as one body after `invoke` — field order is cosmetic JSON-key order and cannot deliver fields progressively; streaming order comes from a generator's yield order, not model field order. Avoid when: tempted to "pre-shape" the JSON model for SSE — SSE needs **separate event schemas** (a sources event, token-delta events, a done/status event) driving a `StreamingResponse`, alongside `ChatResponse`, not a reorder of it.
- Tried (in cutover-1): blanket `except Exception` + exact-byte body assertion in the test. Failed because: the broad catch masks contract bugs into `None`, and the byte-exact assertion couples the test to httpx's internal JSON separators (would flake on a serialization change while the code is correct). Avoid when: reaching for a catch-all "to be safe" — name the failure classes instead.

**Nuances agreed with the user.**
- `render_sources` keeps the user's original `doc.get("title", default)` shape; only the hard `doc["content"]` was softened to `.get("content", "")`. The title fallback semantics were left as the original design on the user's call.
- The unit test proves only the **client half** of the soft degrade (a `false` flag still yields a `ChatResult`); whether `st.warning` actually fires is UI-layer and belongs to the manual smoke test, not the client test.
- Migrating the two existing clients (`conversation_client`, `title_generation_client`) onto `http_config` was deferred to a separate cleanup PR to keep the cutover scope tight — so base URL / headers are still duplicated in those two for now.
- The `chat_history -> []` proof for a degraded turn needs fault injection (force the memory write to fail), which a manual Streamlit smoke cannot time reliably; it defers to the backend DB-side write-failure probe. The manual smoke keeps only the positive control (a persisted turn survives reload).
