# model_migration — Log

## Narrative  (2026-08-07)

The trigger was external: `qwen/qwen3-32b` was decommissioned on Groq, so the answer-generation model had to move regardless of quality. The open question was not *which* model, but whether the forced move degraded anything — and whether that could still be measured before the old model became unreachable.

Measuring it meant confronting a gap in the eval harness. `run_generate_e2e_responses.py` hardcoded the inference model, and `run_evals_e2e.py` discarded every field of the generated file except `dataset_path`. A scored result therefore had no record of which model produced it; runs were distinguishable only by filename timestamp, which is information outside the data. The harness was reworked so the generation model and temperature become CLI parameters and land in the generated file's run-level metadata, alongside the retrieval file used. The scoring script then carries that label through into the scored file, deliberately reading it from the generated file rather than accepting it as a CLI flag, so a label can never disagree with the responses it describes. Files predating the field fall back to `"unknown"` instead of crashing. Comparison itself was kept out of both scripts: they measure, they do not interpret.

The run design froze retrieval. Both arms consumed `eval_20260405_063409.json`, the pre-existing retrieval output, so the generator was the only variable. This was a deliberate trade: it makes the model comparison clean, but it also means the numbers describe the generation layer on old context, not the current chain — `RERANK_RATIO = 0.6` was not part of the retrieval that produced these contexts. The scoring cooldown was cut from 30–60s to 1–3s once TPM/TPD limits were raised, while the post-429 backoff was left at 30–60s, since retrying a genuine rate limit after 1–3s only burns the retry budget.

Only the gpt-oss arm could actually be executed. The qwen3 baseline had to be taken from `eval_e2e_20260405_104221.json`, scored on 2026-06-27 — the model was already unreachable. That file predates the metadata work, so it carries no `model` or `retrieval_results_path` field, and its comparability rests on inference (same corpus, same sample count) rather than on recorded fact. This cannot be repaired.

Analysis was done inline rather than scripted: join the two scored files by id, print per-question deltas for both metrics, count wins and losses. That immediately reframed the headline. The correctness gain (14 improved, 6 regressed) held up as a directional signal, but the faithfulness mean turned out to be the residual of two large opposing tails — id=25 at +0.511 against id=14 at −0.500 — which on 25 samples is noise, not a lift. The user's initial reading of the result as a clear win, and the hypothesis that parameter count explained it, were both walked back against the per-question data. The user separately inspected the raw responses and confirmed no chain-of-thought leaked into `predicted_response`, which ruled out `reasoning_format` asymmetry as an artifact of the measurement.

## Result / outcome

The e2e harness is now model-parameterized and its outputs are self-describing: a generated file records the model, temperature and retrieval source; a scored file inherits all of it (f1755b4, results in 5fa4c6d). The migration to `openai/gpt-oss-120b` shipped as 506afcc, measured on 25 questions with retrieval held constant — correctness 0.6315 → 0.6951, faithfulness 0.7753 → 0.8108 — with the honest reading being "correctness improved, faithfulness is unchanged within noise, nothing regressed grossly."

Definition-of-done is met for the migration and for the harness. It is not met as a quality claim about the bot: these figures cover generation on frozen 2026-04-05 retrieval, not the current chain, and the baseline arm can never be reproduced.

## Narrative — second decommissioning, live-chain swap  (2026-08-17)

The trigger repeated, wider. While testing the half-built G3 (`POST /chat`), Groq turned out to have retired the entire llama family — `llama-3.1-8b-instant` and `llama-3.3-70b-versatile` — which the router, query rewrite, chitchat and title generation all depended on. Unlike the first decommissioning (a single answer-model swap), this broke the app end to end: every request died at the router before retrieval even started. Only gpt-oss-120b (answer) and a qwen3 (~27b) survived alongside gpt-oss-20b.

The design question was which survivor becomes the runtime workhorse. The pre-swap instinct was gpt-oss-20b — small, fast, same family as the generator. That was wrong, and the reason is a Groq API detail worth remembering: gpt-oss models cannot disable reasoning. Their `reasoning_effort` only ranges `low`/`medium`/`high`, and the `include_reasoning:false` flag hides reasoning from the output without stopping the model from generating and billing those tokens. qwen3 alone exposes `reasoning_effort="none"` as a real off switch. That flipped the choice: for the runtime paths — a binary chat/RAG classification, a query reformulation, casual chitchat, an 8-word title — reasoning is pure latency and token cost with no upside, so qwen3-none is the correct workhorse and gpt-oss-20b leaves the architecture. This was verified against Groq's reasoning docs and Context7 before writing any code, because the same class of assumption (a plausible-looking model/param that silently misbehaves) is exactly what the first decommissioning punished.

The implementation was small and centralised. `src/rag/config.py` (already edited by the user) points router/rewrite/chitchat/title at qwen3 and keeps gpt-oss-120b for inference; `qa_chain.py` adds `reasoning_effort="none"` to the three runtime `ChatGroq` instances and leaves `inference_llm` on `reasoning_format="parsed"`; `title_generator.py` drops its hardcoded llama id and sources the model from config. One subtlety that cost a verification step: the disable value is the string `"none"`, not Python `None` — `None` drops the kwarg and reasoning comes back on. The eval scripts, which also hardcode dead judge/rewrite ids, were consciously left for a later job; migrating them carries the judge≠generator rule and the dead-epoch caveat with it, so it is not a mechanical find-replace.

## Result / outcome — second migration

The live chain runs again (commit c740dc7). Verified in-process via LangSmith on a simple query: router 260 tokens, rewrite 546 tokens, both with no reasoning blocks, and gpt-oss still producing inference — so `reasoning_effort="none"` is taking effect and the generator path is intact. Because answer + chitchat are built and streamed inside Streamlit (`get_chain`, cached sync connection), that verification needed no backend; only title generation, which routes through FastAPI, requires uvicorn to confirm. Definition-of-done is met for job 1 (the app is unblocked). Job 2 (resume G3) is now unblocked but not done; job 3 (eval scripts) is deferred by choice.

## Narrative — Job 3: eval revival end-to-end  (2026-08-29 → 30)

Job 3 was drained here (branch fix/evals, merged PR #13 → master; then follow-up fixes 578a235 + 696702f). The migration itself was small — swap dead llama ids for config constants — but the real work was the judge. Diagnosis went source-first: confirmed against installed `ragas 0.4.3` that `llm_factory` cannot pass `reasoning_format` and the new `collections` metrics reject a `LangchainLLMWrapper`, so the only path that keeps qwen3's `<think>` out of the parsed field is the *legacy* `ragas.metrics` fed a `LangchainLLMWrapper(ChatGroq(reasoning_format="parsed"))`. That decision, plus rewrite on `reasoning_effort="none"` and a hard `ragas==0.4.3` pin, is in decisions.md.

A 1-item probe went green and looked like proof — but the full 25-question run then failed twice with `LLMDidNotFinishException`, and chasing it taught the two lessons now in decisions.md: qwen3 reasoning eats the `max_tokens` budget (fixed at 10000), and — the subtler one — the RAGAS DiskCache had cached run 1's truncated response, so the max_tokens fix silently did nothing until the cache was cleared. A third failure (`AnswerSimilarity must be set`) was the legacy `AnswerCorrectness` needing its similarity sub-metric built by hand, because calling `single_turn_ascore` directly skips the `.init()` that `evaluate()` would have run. Stages 1–2 outputs were reused so only stage 3 was re-run after that fix.

The run also became a small autopsy on the judge itself: id=22's rock-bottom precision (0.25) was traced by re-asking the judge each of its four documents — all four verdicts were correct, so the score is a retrieval-ranking failure (gold ranked last), not a harsh judge. That is the durable answer to "is 27b judging worse than the dead llama-70b": unmeasurable in the aggregate, but defensible on inspection.

## Result / outcome — Job 3

Eval is alive again on live models. First qwen3-judge baseline on `corpus.json` (n=25, ratio 0.45): recall 0.9567, precision 0.8933, faithfulness 0.8515, answer_correctness 0.8446, no NaN. Old llama-judge result files are archived under `results/archive/`; `docs/README.md`'s v1/v2 table is flagged "(archived results)" rather than overwritten, because the new epoch (qwen3 judge + legacy metrics) confirms nothing against the old. Still deferred by choice: `run_ratio_sweep.py`, `run_rewrite_rerank_calibration.py`, `run_generate_e2e_responses.py` default, and `run_evals_v1.py` keep dead ids (frozen snapshots / lower priority). `corpus_cross_references.json` was skipped (abandoned branch).

## Narrative — Multi-hop hop-recall harness  (2026-08-31)

After job 3 revived the eval on corpus.json, the multi-hop corpus (`corpus_cross_references.json`, 8 questions) still had no runnable metric - RAGAS context_recall cannot answer "did retrieval reach the second cited article". The design was brainstormed to a spec (`docs/superpowers/specs/2026-08-30-multihop-eval-baseline-design.md`) before code: a deterministic hop-recall added to `run_evals_retrieval.py` alongside the RAGAS scores, gold parsed from each row's `link` "A -> B", parents mapped to article numbers. An agent (in a worktree) implemented it; the one integration risk flagged in the spec bit exactly as predicted - `retrieve_parent_contexts` flattened parents to strings and discarded metadata, so it had to return `(contexts, retrieved_dieu)` and read the number before the flatten. The agent verified the parents-lack-`dieu` assumption and fell back to a title regex.

The value came from reading the baseline per-question, not the aggregate. At n=2/3 per group the per-group rates are almost meaningless; the story is in the rows. Single-pass retrieves exactly one of the two gold articles in 6/8 questions and both in only 2 (id=1, id=6) - textbook motivation for a hop-following agent, and a second-angle confirmation of the ratio-era "6/8 miss a gold article". Two things surfaced only from the rows: second_hop_hit (fixed to the citation target B) reports false wins where single-pass drops the source A instead (id=2, id=8), so full_recall is the honest gate; and the Control group - meant as a single-pass-solvable negative control - fails 2/3, so citation-following breaks even within one chapter.

Direction set for the next feature (the agent): build the multi-hop citation-following agent as pattern B (autonomous reasoning) rather than pattern A (graph-backbone), for the reasons in decisions.md 2026-08-31. Early development runs the loop on a local 7-8B model (fits the 12GB 3060 alongside bge-m3 + reranker) with token/hop instrumentation and a hard hop budget, to learn the cost failure modes (context regrows ~O(N²) across hops as each hop re-sends prior observations) safely and for free; final recall/Δ numbers move to the production Groq model, keeping the epoch-bound discipline.

## Result / outcome — Multi-hop hop-recall harness

`run_evals_retrieval.py` now computes hop_recall on `corpus_cross_references.json` alongside RAGAS, emitting per-question `hop_scores` and a per-group `hop_recall_by_group` aggregate in a self-describing result file (`eval_cross-refer_20260830.json`). Definition-of-done for the harness is met: the metric runs on the single-pass chain, produces the "before" baseline, and the old corpus.json path is unaffected. It is a milestone, not a finished feature - the mirror must later call the agent to produce Δ, and the full_recall-primary / dynamic-second_hop redefinition agreed after the baseline is not yet coded.
