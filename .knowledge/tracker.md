## Known limitations / debt left open

- **Eval scripts still call the retired llama ids (deferred job 3).** `run_generate_e2e_responses.py`, `run_evals_e2e.py`, `run_evals_retrieval.py`, `run_ratio_sweep.py`, `run_rewrite_rerank_calibration.py`, `run_evals_v1.py` — any eval run fails until migrated. `JUDGE_MODEL` already sits in `src/rag/config.py` (qwen3) with no live consumer, waiting for this. Migrating carries two rules: judge≠generator (qwen3, not gpt-oss-120b), and the baseline epoch break (the old judge llama-70b is gone, so no pre-2026-08-17 run is comparable).
- **The RAGAS judge on qwen3 is unverified.** The judge goes through `llm_factory` (OpenAI-compat), which has no `reasoning_format="parsed"`, so qwen3 may leak `<think>` into the content field and break RAGAS parsing. The judge wants reasoning ON so it cannot be set to `none`. Check on the first eval run when job 3 lands.
- **A regression was introduced and not fixed: `lru_cache` was never added to the leaf loaders.** 9b0ab52 removed `@st.cache_resource` from `get_embedding_model` and `load_reranker` but put nothing in its place. `evals/v2/scripts/run_rewrite_rerank_calibration.py` calls `get_embedding_model()` at both line 423 and line 775, so it now loads bge-m3 **twice per run** where the Streamlit cache previously covered it. This was identified before the commit and shipped anyway. One decorator fixes it.
- **The async pool lacks the `prepare_threshold=None` guard.** Only `sync_connection.py` disables prepared statements for the Supavisor 6543 pooler. The async pool (title + SQL) will hit intermittent `prepared statement already exists` under any real concurrency over 6543 — add the same guard before that happens. CROSS-CUTTING: any pool over 6543.
- **The FastAPI lifespan loads models that nothing consumes.** uvicorn startup pays the full bge-m3 + bge-reranker-v2-m3 load to serve title routes only. Running Streamlit and uvicorn concurrently holds two copies of both models — do not run both until the frontend switches to HTTP.
- **Ownership is gated by the chat handler, not by the memory layer itself.** G3's `POST .../messages` checks `fetch_conversation_owner` before invoke (404 on mismatch), so the HTTP chat path is guarded. But `get_session_history` and `get_conversation_messages` still do no owner check of their own — any future caller that skips the handler gate re-opens IDOR. AND the guard rests on `X-User-Id`, an unauthenticated spoofable header: until real auth lands, an attacker can impersonate the owner and pass the 404 check outright. Real `user_id` authentication is the priority before this API is exposed.
- **`src/services/background_tasks.py` is dead code and was not deleted.** Nothing calls `fire_and_forget`; title generation moved to FastAPI `BackgroundTasks`. It cannot be migrated either — `add_script_run_ctx` solves a Streamlit-only problem.
- **No concurrency test exists anywhere in the repo.** Every hazard above (shared transaction, pool exhaustion, session bleed, message loss on client disconnect) is reasoned about but unmeasured. The plan agreed: N=5 concurrent requests with distinct `conv_id`s, a deliberately shrunk pool `max_size` to force starvation, and a stubbed LLM — otherwise the test measures Groq's rate limiter.
- **`app.state.embedding_model` and `app.state.reranker_model` are stored but read by nothing.** Only `app.state.rag_chain` has a dependency. Harmless, but they are speculative surface until something needs them.
- **`get_device()` returns `None` on a CPU-only machine** in both `src/rag/embedding_utils.py` and `src/rag/reranker_utils.py` (it only returns `"cuda"`). `embedding_utils` then calls `device.upper()` in its startup print and raises `AttributeError`. Pre-existing, untouched by this feature, and it will surface the first time the backend runs anywhere without a GPU.
- **The gpt-oss migration has no reproducible baseline.** The qwen3-32b arm is a frozen file scored on 2026-06-27 against a decommissioned model; it cannot be re-run, it predates the metadata fields, and its comparability rests on inference (same corpus, same n) rather than recorded fact. Judge/RAGAS drift between 2026-06-27 and 2026-08-07 is unmeasurable. Treat the deltas as one-time, non-repeatable evidence.
- **Faithfulness was NOT shown to improve.** +0.0355 on n=25 with per-question swings up to ±0.5 (10 win / 7 lose / 8 unchanged) is inside the noise. Only answer_correctness (+0.0636, 14 win / 6 lose) is a directional signal. Do not cite the faithfulness number as a gain.
- **Questions that regressed on the model swap are unexplained.** Faithfulness: id=14, 13, 8, 23, 22, 6, 18. Correctness: id=17, 1, 12, 6, 16, 15 (id=6 lost on both). Nobody has looked at why. If a quality complaint arrives later, this list is the only place to start, since the old model cannot be queried for comparison.
- **The model comparison ran on 2026-04-05 retrieval, not the current chain.** Contexts were frozen to isolate the generator, so these figures describe answer generation only. No end-to-end number exists for the live combination of RERANK_RATIO 0.6 + gpt-oss-120b.
- **The e2e evidence for ratio 0.45 is inside the noise band.** Aggregates improved (faithfulness 0.8095 → 0.8639, correctness 0.6797 → 0.7118) but the per-question split is 6 win / 5 lose and 13 win / 12 lose on n=25 with swings up to ±0.5. The retrieval numbers (recall 0.94 → 1.00, precision 0.9433 → 0.9667) are the trustworthy half; the e2e half is directional only. Neither has been repeated, and query rewrite runs at temperature 0.2 so a re-run will not reproduce these figures exactly.
- **The multi-hop corpus is 8 self-authored questions.** `corpus_cross_references.json` was written in the same session that used it to judge the ratio, sampled from citation edges to avoid reverse-engineering the mechanism, but it has never been reviewed by anyone else and its gold sets are regex-extracted from the reference text. The 0.45 knee rests on it plus 2 multi-hop items in `corpus.json`.
- **6 of 8 multi-hop questions still miss a gold article at 0.45.** Their second article needs ratios between 0.14 and 0.05 and several sit beyond rank 5, i.e. beyond `RERANK_MAX_CHILDREN`. Lowering further buys nothing measurable and raising the cap is worth about one gold corpus-wide, so these are left unsolved — they are a retrieval-recall problem, not a thresholding one.
- **Degree metadata is committed dead code.** `dieu`/`chuong`/`ap_dung_*` ride on every child and `data_quyche/{cross_references,degree_scope}.json` must be regenerated before any re-ingestion (the splitter raises `FileNotFoundError` without the second), yet nothing reads the fields. Kept deliberately as a record of a rejected hypothesis; delete it if the maintenance cost ever exceeds that value.
- **Query expansion always emits exactly 3 sub-queries**, for all 85 questions measured, regardless of complexity — the prompt's "maximum 3" behaves as "always 3". No complexity signal is available from that step, and the expansion does not adapt to the question as its design implies.
- **`eval_retrieval_ratio_20260708.json` is not a valid baseline for anything.** Its contexts carry an "Điều-only" prefix that no committed version of the eval script produces; it came from uncommitted local edits and cannot be regenerated. Left in the repo as history only.
- **`run_rerank_calibration.py` and `run_rewrite_rerank_calibration.py` still carry a stale default dataset path** (`evals/datasets/reranker_abbreviation.json`, which does not exist) alongside the frozen `MAX_RERANK_CANDIDATES = 20` noted below.
- **Negative reranker scores invert the ratio rule.** `cutoff = top_score * ratio` only orders correctly for `top_score > 0`; if top-1 scores negative the cutoff sits *above* it and only top-1 survives. Not observed on the current corpus (bge-reranker-v2-m3 sigmoid output), so left unguarded — revisit if the reranker model or its score range changes.
- **The calibration script is a frozen snapshot, not a repeatable mirror.** `run_rewrite_rerank_calibration.py` keeps `MAX_RERANK_CANDIDATES = 20` and a hardcoded `RETRIEVER_K`, so it reflects production *as of 2026-08-06* — before `fab3e07` removed the pre-rerank top-20 truncation. That is deliberate: freezing it is what keeps `ab_phrasing_20260806_163755.json` reproducible from the committed code. It does mean the script is NOT the "eval mirrors production" contract that applies to `evals/v2` retrieval eval. Before any future ratio re-sweep, re-align it with the current chain first, otherwise the new numbers describe a pipeline that no longer exists.
- **Out-of-scope detection has no owner.** Dropping the floor means the reranker no longer rejects off-topic queries ("giá vàng hôm nay"); "empty context" now fires only on a zero-candidate pool, which hybrid retrieval almost never produces. Needs the router (extend 'chat'/'RAG' to include out-of-scope) or the answer prompt to carry it. Currently unhandled.
- **Wrong-degree-level retrieval was misdiagnosed, and the proposed fix is now closed.** The `bậc`+`chương` metadata was built and the degree-aware selection rule was simulated against 93 questions: it changed one, which the 0.45 retune fixes on its own. Do not reopen degree filtering without first showing that a wrong-degree document is *outranking* gold — see `features/cross_reference/decisions.md`. What remains genuinely unsolved is the recall tail (gold beyond rank 5), which is a retrieval problem, not a degree or thresholding one.
- **BM25 is case-sensitive and never re-checked.** `default_preprocessing_func` is a bare `str.split()`. Lowercasing moved gold Điều 12 from rank 10 → 4 on one smoke-tested question but did not change pool membership in that sample, and membership on the full corpus was never measured. Cheapest untested lever left.
- **Abbreviation-collapse (id=4/11) and table-comprehension (id=19) are out of scope here** and deferred to query-normalization and parser/splitter layers respectively.
- **Calibration set is 26 paired questions.** The worst-case gold tail that sets the ratio knee is effectively a single sample; 0.6 is a defensible knee, not a proven optimum. Re-sweep when the corpus grows, retrieval changes, or the reranker model changes.
- **Multi-hop and numeric-specific query types are underrepresented** in the corpus (only single + table); their score distributions are unmeasured, so the ratio's behaviour on them is an extrapolation.
