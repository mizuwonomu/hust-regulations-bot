## Known limitations / debt left open

- **borrow-1's ownership SELECT returns the conn `INTRANS` on the existing-conversation path.** uvicorn logs `psycopg_pool` WARNING `rolling back returned connection: <... [INTRANS] ...>` from turn-2 on. Cause: borrow-1 commits only when it eager-creates (`owner is None`); an existing conversation runs a read-only SELECT (opens a tx under non-autocommit) then `putconn` without commit/rollback, so the pool auto-rolls-back. Benign (read-only) but log noise + one extra rollback round-trip per existing-conv turn — and after the de-wrap borrow-1 also runs `read_history`'s SELECTs on the same uncommitted connection, so the `INTRANS` return is now the normal path, not just the eager-create-skip case. Tidy-up: autocommit the ownership+read borrow or `rollback()` before `putconn`.
- **RESOLVED (de-wrapper split, 2026-08-29): the conn-pin and `MemoryStatus` are gone.** Memory is now explicit `read_history` (borrow-1) + `persist_turn` (short post-chain borrow); the chain holds no connection, and the write exception propagates so no mailbox is needed. See `decisions.md` "De-wrapper memory split".
- **Job 3 PARTIALLY DONE (branch fix/evals, 2026-08-29).** The two live-path scripts are migrated: `run_evals_retrieval.py` and `run_evals_e2e.py` now read `JUDGE_MODEL` / `QUERY_REWRITE_MODEL` from config (qwen3), rewrite runs `reasoning_effort="none"`, and the judge moved to `LangchainLLMWrapper` + `ChatGroq(reasoning_format="parsed")` (see decisions.md "Job 3"). Verified on a 1-item retrieval probe (recall 1.0 / precision 0.75, no NaN). STILL open: the full run (25 + 8) has not been executed, and `run_ratio_sweep.py`, `run_rewrite_rerank_calibration.py`, `run_generate_e2e_responses.py`, `run_evals_v1.py` still carry dead ids (frozen snapshots / lower priority). The two rules still hold: judge≠generator (qwen3, not gpt-oss-120b) and the baseline epoch break (no pre-2026-08-17 run is comparable), now compounded by a second break — legacy metrics ≠ collections.
- **RESOLVED (job 3, fix/evals, 2026-08-29): the qwen3 judge `<think>` leak.** The judge is no longer built via `llm_factory` (its OpenAI-compat path cannot pass `reasoning_format`, and the new `ragas.metrics.collections` rejects a LangchainLLMWrapper anyway); it now uses `LangchainLLMWrapper(ChatGroq(reasoning_format="parsed"))` on the legacy `ragas.metrics`, which splits reasoning into its own field and leaves `content` clean. Verified: 1-item probe returned finite precision `0.7499999999625` (RAGAS parsed per-statement verdicts, so no `<think>` in content). The judge keeps reasoning ON (parsed, not `none`) as required. See decisions.md "Job 3".
- **A regression was introduced and not fixed: `lru_cache` was never added to the leaf loaders.** 9b0ab52 removed `@st.cache_resource` from `get_embedding_model` and `load_reranker` but put nothing in its place. `evals/v2/scripts/run_rewrite_rerank_calibration.py` calls `get_embedding_model()` at both line 423 and line 775, so it now loads bge-m3 **twice per run** where the Streamlit cache previously covered it. This was identified before the commit and shipped anyway. One decorator fixes it.
- **`prepare_threshold=None` over Supavisor 6543 — FIXED for both pools, and the rule is WIDER than first recorded.** Both `sync_connection.py` and `async_connection.py` now disable prepared statements, guarded by `tests/unit/test_pool_config.py`. The rule was written as "any pool over 6543"; that is too narrow — it applies to **any connection**, pooled or not. Proof: `admin_conn` in `tests/conftest.py` is a plain `psycopg.connect` and died with `DuplicatePreparedStatement: prepared statement "_pg3_0" already exists` after enough runs, because Supavisor reuses backends across clients and statements from a previous run linger. CROSS-CUTTING: **every** connection over 6543 needs the guard.
- **VERIFIED 2026-08-21: production `PoolTimeout` (30s) is unreachable behind the anyio threadpool gate.** Starlette's default limiter is 40 tokens and it does bind (measured: peak concurrent `def` handlers = exactly 40). Only 40 requests are ever in flight and 10 hold connections, so the queue depth that determines wait time is 30 → ⌈30/10⌉ = 3 waves × 4s = 12s. Direct measurement at production config (pool 10, turn 4s, timeout 30s, N=90): **max pool wait 12.31s, p95 12.30s, PoolTimeout count 0**. Overload therefore surfaces as unbounded latency (threadpool queue), never as PoolTimeout, so the capacity "exceeds" arm must use a synthetic short timeout. `PoolTimeout → 503` remains debt but only matters if the threadpool grows or the pool timeout shrinks.
- **`requests_waiting` from `pool.get_stats()` is NOT a trustworthy gauge of live queue depth.** It reads `len(self._waiting)`, a live deque, yet measured peaks exceed the number of threads that can possibly be blocked: 40 with 40 handlers, and **62 during the timeout-churn arm** where only 40 threads exist. Entries linger after their waiter was served or timed out. Only `saw_contention` (> 0) is a safe assertion; never cite peak-waiting as queue depth.
- **Moving the test target to Supabase silently disabled `test_f` and degraded `test_e`.** Supavisor strips `application_name`, which is how both tests locate their own pool's backends in `pg_stat_activity` before `pg_terminate_backend`. Test (e) survives by dropping only the pid-replacement assertion and keeping the two load-bearing ones (no phantom write, `memory_persisted=false`); test (f) has no fallback and is skipped. Both still pass on localhost. Anyone trusting these probes must know which target they ran against.
- **The read-path JOIN turned eager-create into a hard dependency, and production already has 16 orphan sessions.** `fetch_conversation_messages` joins `conversations` to enforce ownership, so a `chat_history` row whose `session_id` has no `conversations` row is now **unreadable**. Measured on production: **16 of 41 distinct sessions are orphans** — legacy from before G3 added `claim_conversation`. No user-facing impact today because the sidebar lists from `conversations`, so an orphan is never selectable. But from now on `claim_conversation` MUST run before the first memory write or that turn disappears from the read path. Currently guaranteed by `chat.py` borrow-1 only.
- **Test-schema parity has three axes, not one: column type, index set, and the tool version that created the table.** All three bit during this feature. (1) `langchain_postgres`'s current `create_tables` makes `session_id uuid` while production `public.chat_history` (older wrapper) is `text` — both test schemas were ALTERed to `text`. (2) Neither test schema had `idx_conversations_user_id`, which production has, so `list_user_conversations` seq-scanned in test and index-scanned in production, making every latency figure optimistically wrong — index created on both. (3) The plan's instruction "create it with the wrapper" is insufficient on its own: the wrapper yields the shape of the *current* version, production carries the shape of the version that created it. Always diff the new schema against `public` and ALTER to match. See `docs/testing-setup.md`.
- **RESOLVED (G5, b41c19f): `POOL_TIMEOUT_SECONDS` placement.** Moved out of `sync_connection.py` (which `async_connection.py` had imported — a wrong-direction sibling dependency) into `src/database/pool_config.py`, together with the `min_size`/`max_size` literals; both pools now import the constants, and the async pool picked up the `prepare_threshold=None` guard there. See `features/backend_migration/decisions.md` (G5).
- **The FastAPI lifespan loads models that nothing consumes.** uvicorn startup pays the full bge-m3 + bge-reranker-v2-m3 load to serve title routes only. UPDATE (G6, 2026-08-26): the *double* model-load is gone — the frontend now loads no models, so Streamlit + uvicorn can run together safely. What remains is the backend-side waste: the lifespan still loads both models even though only the title route (which needs neither) is a live consumer of that state.
- **Ownership is gated by the chat handler, not by the memory layer itself.** G3's `POST .../messages` checks `fetch_conversation_owner` before invoke (404 on mismatch), so the HTTP chat path is guarded. But `get_session_history` and `get_conversation_messages` still do no owner check of their own — any future caller that skips the handler gate re-opens IDOR. AND the guard rests on `X-User-Id`, an unauthenticated spoofable header: until real auth lands, an attacker can impersonate the owner and pass the 404 check outright. Real `user_id` authentication is the priority before this API is exposed.
- **`src/services/background_tasks.py` is dead code and was not deleted.** Nothing calls `fire_and_forget`; title generation moved to FastAPI `BackgroundTasks`. It cannot be migrated either — `add_script_run_ctx` solves a Streamlit-only problem.
- **No guard exists for the history-READ path (`_enter_history` / `load_history`).** `test_f` claims to cover a read failure but kills every pooled connection *before* the request, so it dies at borrow-1 in `fetch_conversation_owner` and never enters `invoke` — proof: it finishes in ~0.14s against a 0.3s stub sleep. The docstring now says so honestly, but the gap is real. Reaching the actual history read needs the connection killed in the few-millisecond window between the two borrows, which `pg_terminate_backend` cannot time reliably; it needs a different mechanism (inject a delay between borrows, or fault-inject at the `get_session_history` layer instead of killing a real connection).
- **Fault injection does not cover silent network loss.** `pg_terminate_backend` models a server closing the socket cleanly, which psycopg detects on the next I/O. TCP half-open (cut cable, firewall DROP, a pooler vanishing without FIN) leaves the connection looking alive until TCP timeout and can *hang* rather than raise. Covering it needs packet-level injection (iptables DROP, toxiproxy). Relevant because Supavisor sits in front of production.

The chosen policy was soft-degrade, not hard error or silent retry. Still open: no LangSmith span / metadata records the flag; only the UI and server-side logging see it.

- **Faithfulness was NOT shown to improve.** +0.0355 on n=25 with per-question swings up to ±0.5 (10 win / 7 lose / 8 unchanged) is inside the noise. Only answer_correctness (+0.0636, 14 win / 6 lose) is a directional signal. Do not cite the faithfulness number as a gain.
- **Questions that regressed on the model swap are unexplained.** Faithfulness: id=14, 13, 8, 23, 22, 6, 18. Correctness: id=17, 1, 12, 6, 16, 15 (id=6 lost on both). Nobody has looked at why. - **The model comparison ran on 2026-04-05 retrieval, not the current chain.** Contexts were frozen to isolate the generator, so these figures describe answer generation only. No end-to-end number exists for the live combination of RERANK_RATIO 0.6 + gpt-oss-120b.
- **The e2e evidence for ratio 0.45 is inside the noise band.** Aggregates improved (faithfulness 0.8095 → 0.8639, correctness 0.6797 → 0.7118) but the per-question split is 6 win / 5 lose and 13 win / 12 lose on n=25 with swings up to ±0.5. The retrieval numbers (recall 0.94 → 1.00, precision 0.9433 → 0.9667) are the trustworthy half; the e2e half is directional only. Neither has been repeated, and query rewrite runs at temperature 0.2 so a re-run will not reproduce these figures exactly.
- **The multi-hop corpus is 8 self-authored questions.** `corpus_cross_references.json` was written in the same session that used it to judge the ratio, sampled from citation edges to avoid reverse-engineering the mechanism, but it has never been reviewed by anyone else and its gold sets are regex-extracted from the reference text. The 0.45 knee rests on it plus 2 multi-hop items in `corpus.json`.
- **6 of 8 multi-hop questions still miss a gold article at 0.45.** Their second article needs ratios between 0.14 and 0.05 and several sit beyond rank 5, i.e. beyond `RERANK_MAX_CHILDREN`. Lowering further buys nothing measurable and raising the cap is worth about one gold corpus-wide, so these are left unsolved — they are a retrieval-recall problem, not a thresholding one.
- **Degree metadata is committed dead code.** `dieu`/`chuong`/`ap_dung_*` ride on every child and `data_quyche/{cross_references,degree_scope}.json` must be regenerated before any re-ingestion (the splitter raises `FileNotFoundError` without the second), yet nothing reads the fields. Kept deliberately as a record of a rejected hypothesis; delete it if the maintenance cost ever exceeds that value.
- **Query expansion always emits exactly 3 sub-queries**, for all 85 questions measured, regardless of complexity — the prompt's "maximum 3" behaves as "always 3". No complexity signal is available from that step, and the expansion does not adapt to the question as its design implies.
- **`eval_retrieval_ratio_20260708.json` is not a valid baseline for anything.** Its contexts carry an "Điều-only" prefix that no committed version of the eval script produces; it came from uncommitted local edits and cannot be regenerated. Left in the repo as history only.
- **`run_rerank_calibration.py` and `run_rewrite_rerank_calibration.py` still carry a stale default dataset path** (`evals/datasets/reranker_abbreviation.json`, which does not exist) alongside the frozen `MAX_RERANK_CANDIDATES = 20` noted below.
- **Negative reranker scores invert the ratio rule.** `cutoff = top_score * ratio` only orders correctly for `top_score > 0`; if top-1 scores negative the cutoff sits *above* it and only top-1 survives. Not observed on the current corpus (bge-reranker-v2-m3 sigmoid output), so left unguarded — revisit if the reranker model or its score range changes.
- **The calibration script is a frozen snapshot, not a repeatable mirror.** `run_rewrite_rerank_calibration.py` keeps `MAX_RERANK_CANDIDATES = 20` and a hardcoded `RETRIEVER_K`, so it reflects production *as of 2026-08-06* — before `fab3e07` removed the pre-rerank top-20 truncation. That is deliberate: freezing it is what keeps `ab_phrasing_20260806_163755.json` reproducible from the committed code. It does mean the script is NOT the "eval mirrors production" contract that applies to `evals/v2` retrieval eval. Before any future ratio re-sweep, re-align it with the current chain first, otherwise the new numbers describe a pipeline that no longer exists.
- **Out-of-scope detection has no owner.** Dropping the floor means the reranker no longer rejects off-topic queries ("giá vàng hôm nay"); "empty context" now fires only on a zero-candidate pool, which hybrid retrieval almost never produces. Needs the router (extend 'chat'/'RAG' to include out-of-scope) or the answer prompt to carry it. Currently unhandled.
- **Wrong-degree-level retrieval was misdiagnosed, and the proposed fix is now closed.** The `bậc`+`chương` metadata was built and the degree-aware selection rule was simulated against 93 questions: it changed one, which the 0.45 retune fixes on its own. Do not reopen degree filtering without first showing that a wrong-degree document is *outranking* gold — see `features/cross_reference/decisions.md`. What remains genuinely unsolved is the recall tail (gold beyond rank 5), which is a retrieval problem, not a degree or thresholding one.
- **BM25 is case-sensitive and never re-checked.** `default_preprocessing_func` is a bare `str.split()`. Lowercasing moved gold Điều 12 from rank 10 → 4 on one smoke-tested question but did not change pool membership in that sample, and membership on the full corpus was never measured. Cheapest untested lever left.
- **Abbreviation-collapse (id=4/11) and table-comprehension (id=19) are out of scope here** and deferred to query-normalization and parser/splitter layers respectively.
- **Calibration set is 26 paired questions.** The worst-case gold tail that sets the ratio knee is effectively a single sample; 0.6 is a defensible knee, not a proven optimum. Re-sweep when the corpus grows, retrieval changes, or the reranker model changes.
- **Multi-hop and numeric-specific query types are underrepresented** in the corpus (only single + table); their score distributions are unmeasured, so the ratio's behaviour on them is an extrapolation.
