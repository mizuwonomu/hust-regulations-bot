# Knowledge Index — HUST Regulations Bot

Vietnamese RAG chatbot over HUST academic regulations (Quy chế đào tạo).

Cross-cutting pointers (read before touching the named layer):
- **Reranker score is NOT comparable across queries** — a cross-encoder score of 0.9 and 0.0007 can both mean "most relevant doc for this query". Any logic that treats an absolute reranker score as a global threshold is unsound. This killed the hard-floor design and constrains every future gating idea. See `features/rerank_ratio/decisions.md`.
- **Post-rerank child selection is a relative ratio to top-1** (`RERANK_RATIO = 0.45`, `src/rag/config.py`), applied in `retreive_parents._apply_score_ratio` (rule shipped 9f48018 at 0.6, retuned to 0.45 in d7611fd, 2026-08-13). There is no absolute floor and no out-of-scope gate in the rerank layer; empty context now means only "candidate pool was empty". The ratio is a *score* threshold (`cutoff = top1 × ratio`), never a document quantile. Any retune must include multi-hop questions: 0.6 was calibrated on an all-single-hop set and cut the second article of multi-hop golds. See `features/rerank_ratio/` and `features/cross_reference/`.
- **Degree filtering has been tested and rejected — do not rebuild it.** Children carry `dieu`/`chuong`/`ap_dung_*` metadata, but no retrieval code reads them and none should: across 93 questions a degree-aware selection rule changed exactly one, which the ratio retune fixes alone. Before treating a failure as "wrong degree level", confirm the wrong-degree document is actually *outranking* gold. See `features/cross_reference/decisions.md`.
- **Faithfulness must never be read without answer_correctness.** A retrieval failure produces the deterministic refusal, which scores ~1.0 faithfulness because it asserts nothing — high faithfulness can therefore be a symptom of broken retrieval, not of quality. See `features/cross_reference/decisions.md`.
- **Any metadata gate on retrieval must sit after the hybrid merge.** `BM25Retriever` is built from in-memory documents and has no metadata filter, so a Chroma `where` clause filters only the dense arm and leaves the pool half-filtered — and it changes `k` semantics, invalidating earlier baselines.
- **Groq models are retired without notice — this has happened twice.** `qwen/qwen3-32b` was decommissioned mid-project (forcing the answer-model swap to gpt-oss-120b), then on 2026-08-17 the whole llama family (`llama-3.1-8b-instant`, `llama-3.3-70b-versatile`) went too, breaking router/rewrite/chitchat/title at once. Every Groq model id in this repo is a live external dependency that can disappear; a model choice here is never freely reversible, because the model you would revert *to* may no longer serve requests. Only gpt-oss (20b/120b) and one qwen3 (~27b) currently survive. Note gpt-oss models **cannot disable reasoning** (`reasoning_effort` only low/medium/high; `include_reasoning:false` hides but still bills reasoning tokens) — only qwen3 supports `reasoning_effort="none"` (the string, not Python `None`). See `features/model_migration/decisions.md`.
- **Eval result files must be self-describing** — a scored file records the generation model, temperature and the retrieval file it consumed, and the scoring script inherits that label from the generated file rather than from a CLI flag. Distinguishing runs by filename timestamp is not sufficient, and a hand-typed label can outlive the truth it misstates. See `features/model_migration/`.
- **LangChain swallows history-WRITE errors but not history-READ errors — never trust a 200 to mean "the turn was saved".** `RunnableWithMessageHistory` attaches the read as a `RunnableLambda` inside the pipeline (`load_history`) so its exceptions propagate normally, but attaches the write as an `on_end` listener (`_exit_history`), and `CallbackManager.handle_event` logs listener exceptions as warnings instead of re-raising them (`raise_error` defaults to `False` and no langchain_core tracer overrides it). A DB failure during the write therefore produced a plain 200 with the turn silently dropped, and — because the write is not a Runnable — it emits **no LangSmith span**, so the failure is invisible in traces too. This is now moot in-repo: the wrapper was removed (2026-08-29) and memory is written by an explicit `persist_turn` whose exception propagates on its own, so `MemoryStatus` is gone. Keep the lesson whenever reaching for callback/listener-based persistence — a listener's exception does not become a failed request. See `features/backend_migration/decisions.md` (G4 + "De-wrapper memory split").
- **PDR contract** — retrieval searches *child* chunks; final answer context is *parent* documents. Child `doc_id` maps back to parent. Breaking this breaks retrieval, splitting and storage at once.

## Architecture (current)

Two cooperating surfaces over one shared core.

**`frontend/` — Streamlit UI.** After the chat cutover the entry point `frontend/app.py` builds and loads **nothing** — no embedding model, no reranker, no chain. It packs a single field into the frozen `AppDeps` dataclass (`frontend/deps.py`): `title_generation_scheduler`. `model_loader.py` and `connection_provider.py` are deleted; `frontend/` imports neither `src.rag` nor `src.database` on any path, which is what lets Streamlit and uvicorn run together without a double model-load. Everything downstream pulls from `deps` — wiring changes belong here, not inside components. Components: `sidebar.py` (conversation list), `sidebar_title_polling.py` (polls `GET .../title`), `source_panel.py` (renders the sources list — now plain wire dicts `{title, content, doc_id}` from the chat response, not LangChain `Document`s), `new_chat.py`, `feedback.py`. Services: `conversation_loader.py`, `feedback_repo.py` (appends to `feedback_log.csv`), `title_generation_client.py`, `conversation_client.py` (read path), and the chat path's `chat_client.py` (httpx `send_message`) plus `http_config.py` (shared base URL, `X-User-Id` header helper, 4-phase chat timeout). Workflows: `chat_flow.py` (orchestrates a turn — now over HTTP via `chat_client.send_message`, renders answer + sources as one block, soft-warns when `memory_persisted=false`, hard-errors only on a `None` result, schedules title on first exchange); `chat_stream.py` is the live SSE render path (`stream_handler` → `st.write_stream`, `classify_turn_outcome` → complete/partial/no_answer), consuming `chat_stream_client.py` (`stream_message` → `ChatTokenStream`, an httpx-sse client that opens eagerly so 404/non-200/transport → `None`, and carries token text plus a `sources`/`memory_persisted`/`error` side-channel). Streamlit session state is the frontend control plane — check rerun behaviour before changing chat/sidebar/feedback/title flow.

**`src/api/` — FastAPI backend.** Owns conversation title generation and now a chat turn. `main.py` mounts `routes/titles.py`, `routes/chat.py`, `routes/chat_stream.py` (the SSE token-streaming twin of `chat.py`), and `routes/conversations.py` (the async **read** path: `GET /conversations` lists a user's conversations, `GET /conversations/{id}/messages` returns normalized history — ownership gated in SQL *and* re-checked in the handler, 404 on mismatch); `lifespan.py` opens a global async psycopg pool plus a sync pool (`app.state.sync_db_pool`); `dependencies.py` injects `get_db_pool`, `get_sync_db_pool`, `get_rag_chain`, and `get_current_user_id` (from the `X-User-Id` header, default `user_vjp_pro_1` — unauthenticated/spoofable, see the ownership note). `POST /conversations/{id}/messages` (`routes/chat.py`, schemas in `schemas/chat.py`) is a plain `def` handler so Starlette runs the blocking chain in the threadpool; it borrows a sync-pool connection twice — a short borrow for ownership check + eager-create + history read (`fetch_conversation_owner` / `claim_conversation` / `read_history`), then the chain runs holding **no** connection, and a short write borrow persists the turn (`persist_turn`). Owner mismatch → 404 (never leak existence); `invoke` only, no streaming yet. The handler also owns the **memory-persist signal**, now without a mailbox: `persist_turn` runs in its own `try/except` and the caught exception sets `memory_persisted=false` on `ChatResponse` (logged server-side). A failed memory write does **not** fail the request — it returns 200 with the answer plus `memory_persisted=false`. The **read** path is now over HTTP: `sidebar.py` and `conversation_loader.py` call `frontend/services/conversation_client.py` (httpx) instead of `src.database`, so `frontend/` no longer imports the DB on that path (only `connection_provider.py` remains). The loader returns a `bool` and the sidebar reruns only on a successful load — a guard against the rerun loop the soft-fail HTTP path would otherwise create. The **chat** path is now over HTTP too: `chat_flow.py` calls `frontend/services/chat_client.py` (`POST /conversations/{id}/messages`) instead of building and invoking a chain in-process. The client is **fail-loud on a malformed 200** (a missing `answer` or non-JSON body raises; only 404 and transport errors become `None`), and a `memory_persisted=false` response still yields a `ChatResult` that the UI surfaces as a soft `st.warning`. Token streaming shipped as **step 3** (`POST /conversations/{id}/messages/stream`, commits 803573b→f0da5a3, 2026-08-28): an `async def` handler streaming `astream` deltas over SSE (event schemas `sources`/`token`/`done`/`error` in `schemas/chat_stream.py`), reusing the two-borrow pattern via a non-blocking poll-acquire (`_acquire_conn`) so a pool-wait never pins an anyio thread. borrow-1 `PoolTimeout` becomes a real 500; a mid-stream chain failure (stream already 200-committed) becomes an `error` event. The **de-wrapper memory split** then shipped (2026-08-29): `RunnableWithMessageHistory` is removed, history is read in borrow-1 and the turn written by an explicit `persist_turn` in a short post-`astream` borrow, so no connection is pinned across the chain and `MemoryStatus` is gone; a post-200 write failure degrades to `done(memory_persisted=false)`, never an `error` (the answer already streamed). See `features/backend_migration/decisions.md`.

**`src/rag/` — the chain.** `qa_chain.py` builds one history-aware runnable: router → query expansion → hybrid retrieval → rerank → parent reconstruction → answer generation. Memory is no longer part of the chain — `chat_history` is a plain input key (the prompts keep `MessagesPlaceholder("chat_history")`), and the FastAPI handler reads history in and persists the turn out (`RunnableWithMessageHistory` removed 2026-08-29, see `src/database`). Query-time pipeline: (1) router (qwen3 `reasoning_effort="none"`, Groq) classifies `chat` vs `RAG`, casual chat bypasses retrieval (also qwen3 no-think) and returns `{answer, context: []}`; (2) query expansion (qwen3 `reasoning_effort="none"` + `PydanticOutputParser`) produces up to 3 standalone Vietnamese subqueries, falling back to the original question; (3) hybrid retrieval — Chroma dense (collection `split_parents`, `BAAI/bge-m3`) plus BM25 over child chunks, equal weights, dedup by page content, `RETRIEVER_TOP_K=15`; (4) rerank — every deduped candidate is scored against the **original** user question (not the subqueries — subqueries buy recall, the reranker must protect precision), then selected by the relative ratio rule above and capped by `RERANK_MAX_CHILDREN`; (5) parent reconstruction — parents fetched from `doc_store_pdr/`, capped at 4, formatted as numbered sources; (6) answer generation (`openai/gpt-oss-120b`, Groq) produces a grounded Vietnamese answer with `[index]` citations and must reply "Thông tin này không có trong quy chế hiện tại." when context lacks the answer; (7) memory — the chain no longer persists anything itself; the FastAPI handler reads history before the chain (`read_history`) and writes the turn after (`persist_turn`), keyed by `conversation_id` (see `src/database`). Rerank scoring and selection are exposed as LangSmith spans (`rerank_children`, `apply_score_ratio`, `fetch_parents`).

**`src/ingestion/` — build time.** `parser.py` runs LlamaParse (`LLAMA_API_KEY`) over `data_quyche/QCDT_2025_DHBK.pdf` and writes Markdown beside it; the parser prompt forces `Chương` → `#` and `Điều` → `###`, and Markdown tables stay Markdown. `splitter.py` reads the Markdown at import time and uses `MarkdownHeaderTextSplitter` on `# Chương` and `### Điều` — **each `Điều` section is a parent document**. Parent content is split into text/table blocks; for tables it injects the table header plus a lead-in sentence from the preceding text block. Blocks become children at `chunk_size=600`, `chunk_overlap=100`; `build_child_metadata` stamps `doc_id` (child → parent), `title`, plus `dieu`, `chuong` and four `ap_dung_*` degree booleans. Those degree fields come from two build-time modules — `reference_parser.py` extracts the Điều→Điều citation graph into `data_quyche/cross_references.json`, and `degree_map.py` turns chapter membership plus dependency edges into `data_quyche/degree_scope.json` (both gitignored; regenerate in that order or the splitter raises `FileNotFoundError`). **The degree fields are stored but deliberately unconsumed** — see the cross-cutting pointer above. `ingest_regulations.py` deletes and rebuilds `chroma_db/` and `doc_store_pdr/`: children embedded with `BAAI/bge-m3` into Chroma collection `split_parents`, parents pickled into a `LocalFileStore` via `EncoderBackedStore`. Both stores are gitignored — regenerate after cloning.

**`src/database/` — Postgres, deliberately split.** Sync (`history_manager.py`, `conversation_queries.py`) serves the FastAPI chat memory path (`connection.py`, the last Streamlit-cache-era opener, was deleted in the de-wrap 2026-08-29); async (`async_connection.py`, `conversation_queries_async.py`) serves FastAPI reads and title generation, including the read queries `list_user_conversations` / `fetch_conversation_messages` / `fetch_conversation_owner_and_title_pool`. Pool sizing and timeout are constants in `pool_config.py` shared by both pools; message normalization is one module, `message_normalizer.py` — both query layers call `normalize_message`, which returns `None` for an unusable row and never raises. Tables: `chat_history` (LangChain messages for memory) and `conversations` (id, user id, title, timestamps). Keep DB work behind the query/helper layer unless changing schema. `history_manager.py` exposes two explicit helpers — `read_history(conn, cid)` (DAO `get_messages`, returns `list[BaseMessage]`) and `persist_turn(conn, cid, question, answer)` (builds `[HumanMessage, AIMessage]` and calls `add_messages`, letting a write exception propagate). `TrackedPostgresHistory`, `MemoryStatus`, `get_postgres_history` and the wrapper plumbing were deleted in the de-wrap (2026-08-29); `PostgresChatMessageHistory` is kept only as the serialization DAO.

**`src/services/` — background work.** `title_generator.py` builds a short Vietnamese title from the first user query + first AI answer (`generate_title_async` is the async entry point). `background_tasks.py` is the sync path: a cached `ThreadPoolExecutor` that attaches the Streamlit script context to background work — title generation must never block the chat input path. `conversation_title_service.py` is the live async orchestrator: validates ownership, re-checks for an existing title (idempotent), loads the first exchange, generates, upserts, commits.

**Title generation flow.** On the first exchange `chat_flow.py` calls `deps.title_generation_scheduler` → `title_generation_client.py` → `POST /conversations/{id}/title-generation` (202, schedules a FastAPI `BackgroundTask`). The sidebar then polls `GET /conversations/{id}/title`. The backend is the source of truth and idempotent. Base URL via `FASTAPI_BASE_URL` (default `http://localhost:8000`).

**`evals/v2/scripts/` — evaluation.** Split by concern: retrieval scoring (context recall + precision) vs generated-response scoring (faithfulness + answer correctness). The retrieval eval **intentionally mirrors production retrieval** (query rewrite → hybrid child retrieval → rerank selection → parent reconstruction) and must be kept aligned when the chain changes. Scripts use rate-limit sleeps and retries (Groq / RAGAS judge calls throttle); the inter-request cooldown is short (1–3s) while the post-429 backoff stays long (30–60s), since retrying a genuine rate limit immediately only burns the retry budget. The generated-response step (`run_generate_e2e_responses.py`) takes `--model`/`--temperature` and writes them into run-level metadata with the retrieval file it consumed; the scoring step (`run_evals_e2e.py`) carries that label through and never accepts it from the CLI. Comparing two scored runs is analysis done inline by joining on `id`, not a function of either script. Rerank calibration lives in `run_rewrite_rerank_calibration.py`, which has a single-distribution mode and an A/B mode (formal vs abbreviated phrasing, paired by id). `run_ratio_sweep.py` answers ratio questions offline: it runs retrieval once per question and persists the full scored list (rank → Điều → score), because the ratio takes no part in retrieval or reranking and only moves the cut on an already-scored list — so every later sweep is arithmetic on the stored file with no API call. The retrieval eval takes `--ratio` to override `RERANK_RATIO` for one run without touching production config, and every result file records its own `config` block (ratio, max children, k, max parents) since two runs differing only by threshold are otherwise indistinguishable. The RAGAS judge is qwen3 via `LangchainLLMWrapper(ChatGroq(reasoning_format="parsed"))` on the **legacy** `ragas.metrics` (the newer `ragas.metrics.collections` rejects the wrapper, and `llm_factory`'s OpenAI-compat path cannot pass `reasoning_format`), with `ragas` pinned `==0.4.3`; the judge needs `max_tokens` set high because qwen3 reasoning tokens count toward the cap (a truncated verdict is `finish_reason="length"`, which RAGAS treats as unfinished), and `AnswerCorrectness` needs its `AnswerSimilarity` built explicitly since a direct `single_turn_ascore` skips `.init()`. Every eval score is epoch-bound (judge model + metric API), so numbers across a judge change are never comparable. Datasets: `corpus.json` (25, RAGAS retrieval/e2e), `corpus_cross_references.json` (8, multi-hop across citation edges), `corpus_reranker{,_abbre}.json` (26 paired, formal vs abbreviated) — **these are separate id spaces; never join them by id**.

## Persistence & UI state

`frontend/state/session_state.py` owns Streamlit state defaults. `conv_id` is the LangChain/Postgres session id; `messages` is the renderable transcript; `last_context` carries sources from the stream to the source panel. `selected_conversation_id`, `conversation_selectbox_id` and `load_selected_conversation` protect sidebar selection from rerun collisions; `title_generation_started` / `pending_sidebar_title_sync` coordinate title generation with reruns. **`chat_stream.py` is the SSE streaming render path** (restored in step 3) — it consumes a `ChatTokenStream` from `chat_stream_client.py`, yields token deltas to `st.write_stream`, and writes `sources` into `last_context` mid-iteration; `classify_turn_outcome` maps the stream's error/token state to complete/partial/no_answer (with `memory_persisted=false` an orthogonal soft warning). Two failure boundaries collapse to one UI "no answer": `stream_message` returns `None` for pre-open failures (404/non-200/transport), and `classify_turn_outcome` returns `no_answer` for an error before the first token.

## When something breaks (most common root causes)

- **Empty/irrelevant answers** → retrieval: missing vector store, stale embedding model, bad child metadata, no parent mapping, or the rerank ratio too strict.
- **Missing sources in UI** → `context` must be captured from the stream before the UI renders sources.
- **Broken memory** → `session_id` mismatch across Streamlit `conv_id`, `RunnableWithMessageHistory`, and Postgres history.
- **Duplicate/stale sidebar conversations** → Streamlit rerun state, not LangChain.
- **Title not appearing** → FastAPI not running, `DATABASE_URL` unset, `FASTAPI_BASE_URL` mismatch, or polling/rerun state in the sidebar.
- **Table answer errors** → parser/splitter table preservation, not the answer prompt.
- **Slow first response** → cached model loading (embedding/reranker), Chroma/BM25 construction, or reranker init — not the LLM call.
- **Feedback not logged** → `feedback.py` writes via `feedback_repo.save_feedback` to `feedback_log.csv`; check the rerun key (`fb_{msg_len}`) and that the last message is an AI turn.

## Working guidelines

- Rebuild the vector store after changing embedding model, splitter metadata, chunk schema, or child/parent mapping.
- Keep the original user question as the reranker scoring query.
- Keep DB work behind the query/helper layer unless changing schema.
- Keep eval changes aligned with production retrieval.
- Comments and prompts in this codebase are largely in Vietnamese — match that style.
